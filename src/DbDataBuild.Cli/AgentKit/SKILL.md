# Working in a dbdatabuild project

dbdatabuild builds analytics tables and views on SQL Server, PostgreSQL and Fabric from SQL written in **DuckDB's dialect**. It is plan-then-apply: nothing reaches a database except through a plan a person has read. Your job is to write models and run the safe commands; a person decides what gets applied.

## Rules that are never negotiable

1. **Never run a command that changes a database or its tracking tables without the person's explicit go-ahead in this conversation**: `connection deploy --apply-plan` (and `--yes`, and `--ack`), `connection refresh`, `connection init --apply`, `connection publish`, `connection seed --apply`. Everything else is safe to run. `connection deploy --write-plan` writes only a plan file; `project compile` and `project model update --write` write only repository files.
2. **Never edit a plan file** (`plans/**/*.plan.yml`). It carries a hash of its own content and applying refuses an edited one. Make a new plan instead.
3. **Never edit `rendered/`** (the generated scripts and `rendered/lowered/*`). Change the model and run `dbdatabuild project compile`; commit the result. `project compile --check` is the CI test that they are current.
4. **Never answer a question about data on the person's behalf**: whether a new column's history was backfilled, whether a missing column is a rename, whether to drop something. Show the question (`connection deploy --write-plan --format json` lists it under `data.open_questions` with its options and the tool's proposal) and ask. Only after the person decides, write the answers file (`--answers`, format in `schemas/answers.schema.json` next to this file) with exactly their choices.
5. **Never set or print the write login** (`DBDATABUILD_<TARGET>_WRITE`) and never put a connection string in a file. Read-only commands use `DBDATABUILD_<TARGET>_READ`.
6. When something fails, run `dbdatabuild help code DDB-nnn` for the code and read the diagnostic's `fix` before changing anything. Do not work around a refusal by changing what it protects.

## How to run it

Always add `--format json`. A command that works on one connection takes its name as the first argument after the command (`connection deploy warehouse --write-plan`, `connection status warehouse marts.orders`); leave it out when the project has one default connection. There is no `--connection` option on these (`project compile --connection` and `project model create --connection` still take a list of connections as a filter). Standard output is exactly one document (`schemas/output.schema.json` next to this file): `exit_code`, `ok`, `data` (a closed shape per command), `diagnostics` (each with `code`, `severity`, `location`, `found`, `supported`, `fix`) and the human text in `messages`. Exit codes: 0 ok, 1 findings (read the diagnostics), 2 usage, 70 a tool bug (report it). Null values are omitted from the document.

| Command | Reads and writes | Use it to |
|---|---|---|
| `project compile [--check]` | project files | check config and models (lowers every query with DuckDB, lints it per target; `data.models` has full metadata), then write `rendered/`; `--check` writes nothing and fails if `rendered/` is out of date |
| `project sample [models]` | project (offline) | run models on generated or supplied rows and see the result (`--rows --seed --limit --data <dir> --declared`) |
| `project tests list [--tag t] [--kind k]` | project (offline) | list the tests with their kind, severity and tags; nothing runs |
| `project tests run [names] [--tag t] [--strict]` | project (offline) | run the project's tests: metadata rules in `tests/metadata/*.sql` (DuckDB SELECTs over the `metadata_*` views that return violations); exit 1 if an error-severity rule returns rows |
| `project show graph [selectors] [--columns \| --column m.c \| --diagram dot\|mermaid]` | project (offline) | the dependency graph and column lineage; what a change to a model or a column reaches |
| `project create [template] [dir]` | project files | list the built-in project templates, or create a ready-to-run example project (mapped models, seeds, staging, marts, tests) |
| `connection seed [connection] [--scale n --replace --apply]` | **connection structure** | create the seeded tables (the mapped models) on a sandbox connection and fill them from the seeds (prints the plan unless `--apply`; write login) |
| `project seed [--seed n --scale n]` | project files | run `seeds/` (DuckDB queries that generate the rows of the mapped models) into `.dbdatabuild/seed.duckdb`; `project sample` uses the same seeds |
| `project show metadata`, `project show loads`, `help matrix`, `help dialects`, `help code <code>` | project (offline) | what the tool knows: types per connection, load operations, what differs per engine, the dialect profiles of read-only origins, a code's meaning |
| `project model create <schema_name.object_name> [--kind view\|full\|incremental_by_unique_key\|incremental_by_time_range] [--connection c]` | project files | scaffold a model in the project's layout: a definition and a placeholder query that runs; replace the query, then `project model update` |
| `project model update [paths] [--offline] --check` / `--write --answers f` | connection (read-only); project files unless `--check` | keep the `.yml` definition in sync with the query, and each mapped model with its table (unless `--offline`); `--check` writes nothing |
| `project import [connection] [schema_name.table_name ...] [--write \| --check]` | connection (read-only); files only with `--write` | export tables and views from the connection as mapped models under `models/`; with no arguments refresh the existing ones; the default shows a diff and writes nothing |
| `project update [selectors] [--offline] [--check]` | connection (read-only); project files unless `--check` | bring in everything that comes from connections: the definitions of the models, the metadata of mapped models and the tables copies read, and the dialect each Flight SQL server reports (committed in `dialects.lock.yml`); online by default, `--offline` reads no connection, `--check` writes nothing and exits 1 if anything would change; a connection with no read login or that cannot be reached is said and skipped |
| `connection compare [connection] <schema_name.table_name> --against <schema_name.table_name> \| --against-schema <schema name> \| --against-connection <connection> [--key a,b] [--show-values]` | connection (read-only) | compare the data of two tables (of one connection, or the same table on another connection or engine, by digests): columns and types, row counts and a key-based row diff done in the engine; counts only unless `--show-values` (ask the person before using it: it prints real data) |
| `project show plan [plan file] [--connection t]` | project (offline) | list the project's plans, or show one: steps with risk, reasons, parameters and exact statements, the report, whether it is intact, and what applying it would need to be allowed. Use it to summarize a plan; it applies nothing |
| `project show refresh [plan] [--connection c] [--resolve]` | project (offline) | the compiled refresh plans: list them, or show one with its members in the order they run, the inputs each load takes and where each default or resolver comes from, what was left out and the hashes; `--resolve` evaluates the `expression` resolvers of the plan now, offline. Plans are declared by `refresh.plans` in `dbdatabuild.yml` and a model's `refresh:` (`refresh: { hourly: incremental, daily: { load: backfill, inputs: { days: 60 } } }`; a folder's `defaults: { refresh: ... }` puts every model beneath it in a plan) |
| `connection inspect` | connection (read-only) | can the tool use the connection: are the logins set, do they connect and as whom, what may they do, are the tracking tables ready (nothing is created to find out) |
| `connection status [plan]`, `connection monitor [plan]` | connection (read-only) | structure (in sync, pending, needs attention), the newest deploy and refresh, the policy, one line per refresh plan; the timeline of events and what needs attention. With a plan: its runs (complete and partial apart) and each member's last success and failure |
| `connection deploy --write-plan` | connection (read-only), plan files | plan a change of structure: write a plan file for a person to read |
| `connection deploy --apply-plan <plan>` (also `--yes`, `--ack kind:name --reason`), `connection refresh [connection] [plan] [selectors] [--only-failed] [--parallel n]` (`--only-failed` repeats the loads the plan's last run left failed, skipped or not run; plan settings `on_failure`, `on_busy`, `max_wait`, `max_runtime`, `expected_every`, `parallel` act; `--parallel n` / `parallel: n` runs up to n loads together once the loads they read are done, `connections.<c>.max_parallel` caps the sessions one refresh opens at a connection, results stay in plan order, a dry run goes one at a time; exit 1 unless the run `completed`) (the loads of a compiled refresh plan, `default` when none is named; selectors are the model grammar plus `load:<name>`; a load named `model.load` runs alone; `--input [model.]name=value` replaces an input and the resolver that would compute it; `--dry-run` also runs the `target` resolvers, read-only, and prints the values it would use; `--check none|project|objects|live`, `--on-fail warn`), `connection init --apply`, `connection publish` | **changes the connection** | only with the person's go-ahead; `connection deploy --apply-plan <plan> --dry-run` changes nothing. A plan that stopped part-way continues when the same plan is applied again |

## If the dbdatabuild tools are available (an MCP server)

When the host has started `dbdatabuild ui mcp` for this project, the commands above are tools named with underscores (`project_compile`, `connection_deploy`, `project_show_plan`, `project_sample`, `project_show_graph`, ...) and this file is also the resource `dbdatabuild://skill`. You cannot start the server yourself: the host does, from its configuration (`dbdatabuild project agent-kit --write --mcp` adds it to `.mcp.json` for Claude Code; `docs/interfaces.md` has the settings for other hosts). If the person wants it and it is not there, tell them that; do not look for a way around it.

- **Use the tools, not the shell, for what they offer.** `--format json` is already on, a tool returns the command's document (also as structured content), paths and model names are relative to the project, and the logins stay in the server's environment. Exit code 1 (findings) is an answer, not a failure of the call.
- **What is not offered is not an oversight.** The commands that change a database (`connection refresh`, `connection init --apply`, `connection seed --apply`, `connection publish`, and `connection deploy` with `--apply-plan`, `--yes` or `--ack`) are left out unless the person started the server with `--allow-writes` (`connection deploy` is then offered to plan, without those options); each run is put to them through the host and runs only if they approve. `connection compare --show-values` and `project sample --data` are never offered (you work without data), and a path outside the project is refused. If a call is refused, say so and say what the person can do; never route around it with the shell.
- **When the person should look or decide, open the interface** instead of pasting into the chat: call `show` (with a screen: `plans`, `lineage`, `models`, `health`, `sample`, `diff`, `tests`, `matrix`), or call `project_show_plan`, `connection_deploy`, `project_show_graph`, `connection_compare` or `project_sample`, and a host that supports MCP Apps shows them the page, with the plan's steps, the questions of the plan to answer, and (if the server was started with `--allow-apply`) their own Apply button. A host that does not support MCP Apps still has `show`: its result is a link to the same page in the person's browser (on the machine the server runs on). Tell the person the link, once; it works once and for ten minutes, and whoever opens it first gets the session, so do not open it yourself; call `show` again for another. Pressing Apply is theirs: you cannot, and you should not describe the plan as applied until they say so.
- **If applying a plan is offered to you** and the host shows the person a confirmation, wait for the answer. If they decline, nothing ran: do not ask again unless they ask you to.
- **Prompts**: the server offers `explore-project`, `add-model`, `change-model`, `fix-findings` and `review-plan`, the loops of this file as ready-made starts. A person may pick one; the rules here still apply.

## Choosing models

Every command that takes models takes selectors: `+model` (it and what it reads), `model+` (it and what depends on it), `2+model`, `@model`, `kind:full`, `connection:postgres`, `tag:finance`, `property:owner=finance`, `path:models/marts`, `changed:origin/main` (what differs from a git ref; add `+` for what depends on it), `a,b` for an intersection, `exclude:<selector>`. `graph --column m.c` shows what a column change reaches. After editing a model, `connection deploy --write-plan changed:HEAD+` plans it and everything downstream.

## The loop for a model change

1. Edit `models/<schema name>/<name>.sql` (and `.yml`; a `.sql` may start with a head, `CREATE TABLE schema_name.object_name WITH (kind = 'incremental_by_unique_key', unique_key = (id)) AS` or `CREATE VIEW schema_name.object_name AS`, which says the name, table or view and the reload options: then the `.yml` leaves out `name:` and `kind:`, and the kind is said in one place). The model name is the `name:` in its definition (`marts.fct_orders`); with the default `model_layout: folder` the path must spell it (`models/marts/fct_orders.sql`), and `dotted` (`marts.fct_orders.sql` anywhere), `object` (`fct_orders.sql` anywhere) and `none` are project choices in `dbdatabuild.yml`: read the layout before creating a file, and never move a model's file to change its name (change `name:`).
2. `project compile` until it is clean (it validates, then writes `rendered/`). Read warnings too: DDB-302 (approximated on an engine), DDB-304 (unverified, Fabric), DDB-223 (a key-based load has no index on its key), DDB-225 (a load slices by a column the engine cannot filter early: an aggregate or window output, a LIMIT). DDB-225 is advice about cost: tell the person and let them choose another column or strategy; do not rewrite their query to make it go away, and do not silence it yourself.
3. `project sample <model>` and look at the rows. This is the fastest way to check logic; it runs in DuckDB only.
4. `project model update --check`; if the declared columns are out of sync (DDB-420), `project model update --write` with answers, or edit the `columns:` by hand.
5. `project compile` again if you changed anything, then commit `rendered/`.
6. `connection deploy --write-plan --format json`. If it has `open_questions`, stop and ask (a parameter of a reload or backfill can be given as `--param model.operation.parameter=value` once the person has chosen the value). Otherwise give the person the plan path and a summary of the steps (`data.plan.steps`: type, risk, description). Risky and destructive steps need their own flags (`--allow-risky`, `--allow-destructive <object>`) when the plan is applied, and that is the person's call.

## Writing a model

A model is a single `SELECT` in DuckDB's dialect, plus a YAML definition. `columns:` is **required** and is the declared output: name, type, `nullable: false` where it can never be NULL.

```yaml
name: marts.fct_orders
kind:
  incremental_by_unique_key:
    unique_key: [order_id]               # must equal grain for incremental_by_unique_key
grain: [order_id]                      # the columns that identify one row; required for incremental kinds
connections: [sqlserver, postgres]         # optional; defaults.connections in dbdatabuild.yml otherwise (a list here adds to it; `connections=:` replaces it)
columns:
  - {name: order_id, type: BIGINT, nullable: false}
  - {name: amount, type: "DECIMAL(14, 2)"}
indexes:                               # only what you declare is created; never inferred from unique_key
  - {name: ux_fct_orders_order_id, columns: [order_id], unique: true}
```

- **Settings can come from the folders above the model.** `defaults:` in `dbdatabuild.yml` and in a folder's `_dbdatabuild.yml` (not a model) set `connections`, `kind`, `hooks`, `rewrites`, `lint_ignore`, `tags` (labels `tag:` selects by) and `properties` (key to value, merged by key; `properties-: [key]` removes one) for every model beneath, root first, the model's own file last, the nearest winning. A list **adds** to what is inherited, a mapping merges by key, a scalar replaces; `key=:` replaces what was inherited, `key-: [x]` removes `x`. `validate` prints `Inherited by <model>: ...` with the file and line. Before you write `connections:` in a model, check whether a folder already sets it.
- **Say what things are, in words.** The project (top of `dbdatabuild.yml`), each connection, each model, each column and each index take `title` (a short name), `description` (free text), `tags` (words) and `properties` (key to one value: text, a number, or `true`/`false`; `owner: finance`, `tier: 1`). They change nothing that is built and nothing is written into the database; they are kept in the metadata documents and, with `connection publish`, in the tracking table `object_info`. Write a description for what a person could not tell from the name, and an `owner` property on a mart. Limits: title 200 characters, description 4000, tag and property key 128, property value 4000 (DDB-243). A column or index writes them inline: `- {name: amount, type: DECIMAL(14, 2), description: "Paid, tax included"}`. `title` and `description` are never inherited; `tags` and `properties` come from `defaults:` like the other settings. A text that looks like a number is quoted to stay text (`code: "007"`).
- **Copies move rows between connections**: `kind: {copy: {from: schema_name.table_name}}` (no `.sql`, no `columns`) is a table on its own connection filled from a model or mapped model on exactly one other connection, a full replace each run. `plan` shows a `transfer` step before the load; `apply` needs the origin connection's read login in the environment (`DBDATABUILD_<ORIGIN>_READ`) as well as the destination's. A query still runs on one connection: to join or shape data from two, copy one into the other first, then build a model. A mapped model on several connections (`connections=: [store_017, store_018]`) is fan-in: its copy needs `slice: {column, value: "${origin.param}", type}` (a connection's `parameters:` say what differs, such as a store id), every run replaces only the rows of the origin it loads, and `apply` names an origin whose table differs from the declaration just before that origin's transfer (DDB-230; `on_mismatch: skip` leaves that origin out, and the origins before it stay loaded). For big tables make a copy incremental: `unique_key: [id]` and `watermark: {column: updated_at, lookback: 3 days}` under `kind` read only rows at or after the newest value the destination holds (rows deleted at the origin are not deleted: a copy that must re-read in full declares a second load, `loads: { default: {...}, full: { strategy: full_replace } }`, and a plan or `connection deploy --op <copy>=full` / `connection refresh <connection> <copy>.full` runs it; `full_replace` of a copy means everything of the origin being loaded, with no watermark bound; there is no flag that re-reads everything). A copy is also a load of a refresh: name it in `refresh:` (`refresh: { hourly: default }`) and `connection refresh <plan>` stages each origin, loads the copy and runs what reads it afterwards; the refresh needs the origins' read logins, and an origin that does not answer ends the copy `failed: origin` (the plan's `on_failure` decides about what reads it). A copy of a native model stays a deploy's.
- **A connection the tool only reads says `readonly`**: `engine: readonly postgres` (the keywords of `engine` come in any order: driver `sqlserver`, `postgres`, `fabric`, `duckdb`, `odbc`, `flightsql`; access `readonly`; a dialect where the driver has none). No `_WRITE` login is read for it, and it is refused as a model's connection, a copy's destination, `tracking.connection` and the target of `connection deploy`, `refresh`, `seed`, `publish`, `init` (DDB-455). It is an origin: a copy, a mapped or native model, a `source` resolver; `connection inspect`, `status`, `compare`, `monitor` and `project import` read it. `dialects:` in `dbdatabuild.yml` holds the profiles for systems with a dialect of their own (`quote`, `parameters`, `ping`, `catalog`, `identifier_case`, `limit`, `types`; `extends: ansi` by default; `dbdatabuild help dialects` lists the fields and the built-ins); an invalid profile is DDB-456. The dialect is the one of the system a connection reaches, not of the server in front of it: a proxy in front of PostgreSQL and SQL Server is two connections, `readonly flightsql postgres` and `readonly flightsql sqlserver`. **A DuckDB file** is an origin too: `engine: readonly duckdb`, the read login's value is the path of the `.duckdb` file (opened read-only) or `:memory:`, and a native query on a `:memory:` connection reads a Parquet or CSV file (`SELECT * FROM read_parquet(${project.file})`); the tool does not print the path. **An ODBC source** is `engine: readonly odbc` (dialect `ansi`, or `readonly odbc my_dialect` with the profile under `dialects:`); its read login is an ODBC connection string or `DSN=name;UID=..;PWD=..`, values are bound by position (`?`, a value used twice is passed twice), `project import` and the structure check read `information_schema` unless the dialect says `catalog: odbc` (the driver's own catalog functions, for a system without `information_schema`) or `catalog: none` (then declare the tables by hand), and `types:` in the dialect maps a type the standard names do not cover. `project import` also writes the indexes where the origin's catalog has them (a DuckDB file, an ODBC driver's statistics) and says plainly where it has none (a Flight SQL server). The machine needs the ODBC driver manager (unixODBC) and the vendor's driver; the tool ships neither, and `connection inspect` says which is missing. **A Flight SQL server** is `engine: readonly flightsql [dialect]`; its read login is `grpc+tls://host:port;token=...` or `;user=..;password=..` (also `token_env`, `token_command`, `ca_file`, `tls_skip_verify`, `header.<name>`), parameters are prepared and bound typed by position, the catalog comes from the server's metadata calls then `information_schema`, and Entra ID/OIDC means a token obtained outside the tool (`token_command` runs a program that prints it). Never set or ask for a write login for a readonly connection. **A Flight SQL connection with no dialect keyword** gets its dialect from the server: `project update` asks it (`GetSqlInfo`), commits the answer in `dialects.lock.yml` (commit that file; do not edit it: DDB-457) and compile and the plans read it offline; without it a copy that reads from the connection is written for `ansi` and compile warns (DDB-458). A keyword in `engine` always wins (an unused entry is DDB-459). A deploy or refresh whose server now reports another dialect fails the origin (DDB-460): run `project update`, show the person the change to the file, and compile again. `project update --check` is the CI form; `--offline` reads no connection; a connection with no read login is skipped with a note, not an error.
- **Tracking is opt-in and can be central.** `tracking: { connection: <name> }` in `dbdatabuild.yml` says which connection keeps the records (drift baselines, DDL and run logs, acknowledgements, history) of every connection written; every record names its connection, and the tracking connection can be another one than the data's (run `connection init <it> --apply` once). With no `tracking:` the tool warns (DDB-232) and records nothing: plans are made from declared against live and every change to an existing object is risky; `tracking: none` chooses that without the warning. `ack`, `report` and `publish-metadata` need tracking.
- **Parameters** (`${scope.name}`): `${project.x}` (`parameters:` in `dbdatabuild.yml`; a folder's `_dbdatabuild.yml` overrides them beneath it), `${connection.x}` (`connections.<name>.parameters`), `${model.x}` (the model's file only), `${origin.x}` (a copy's slice only). A value is text or `{type: DATE, value: "2024-01-01"}` (VARCHAR, BIGINT, INTEGER, SMALLINT, DATE, TIMESTAMP). In a **table** model's query a reference is a value: `WHERE region = ${project.region}` becomes a bound placeholder, never text, so the rendered files do not change with a value; a view cannot use one, and a reference cannot change a table or schema name.
- **Native models** (`kind: {native: {access: select, query: ...}}`, or a `.native.sql` beside the definition) are tables the engine computes from its own text (a table function, `STRING_SPLIT`, `unnest`): declare their columns, put them on one connection, write the text in that engine's dialect (a single SELECT; parameters as `${project.x}`), and read them from ordinary models on that connection (the text is spliced in as a derived table). A **local copy** (`kind: {copy: {from: erp.open_orders}}` on the same connection) lands any model, native or not, as a real table with no transfer. A procedure or function call is `access: command` (`query: EXEC dbo.proc @x = ${project.x}`): the connection must set `allow_native_commands: true`, nothing can read it, and it is only the `from:` of a copy (a transfer, even on its own connection; the step is risky, so a person adds `--allow-risky`). `reads: [models]` puts a native model in the graph and the build order; `track_definition: [dbo.fn_x]` names routines whose definitions are hashed at apply and compared at plan (a change is a warning, DDB-234).
- **Mapped models** (tables that exist and that the tool does not build) are `models/<schema name>/<table>.yml` with `name`, `kind: mapped`, `columns`, optional `grain`, and no `.sql`; a folder can say `defaults: {kind: mapped}` once for everything beneath it. A query can only read mapped models and other models (DDB-218 otherwise). Do not type a mapped model out by hand when the table exists: `import` exports the real columns, types and nullability with the read login (preview first, then `--write`), keeps a `grain` you wrote, and maps unlimited text (`varchar(max)`, `text`) to a bare `VARCHAR` and xml/json to `VARCHAR` too, and leaves out only a column with no representation at all (DDB-226; declare it yourself). It also exports the table's `indexes:` and `foreign_keys:` (read-only facts: never write them to change the database). `import --check` finds mapped models that have gone stale (DDB-227).
- **Inputs** (`inputs:` in a load) are the values a load needs, each with a `type`, a `default` and/or a `resolver`: `{ expression: "current_date - days" }` (DuckDB, evaluated in the tool, no database, the clock frozen for the run, `timezone:` in `dbdatabuild.yml` sets the zone, UTC by default), `{ target: "SELECT max(day) + 1 FROM marts.fct" }` (over the project's models, lowered for the engine, exactly one row, read login), or for a copy `{ source: "..." }` (at the origin). `provides: [start, end]` lets one resolver answer several inputs by column name; `on_null: fail | initial | skip_load` says what NULL means. `start` and `end` of a range load are its inputs; an input called `end` is written `"end"` inside an expression. `project compile` checks every resolver (DDB-451, a circle is DDB-452).
- **Kinds** (the word is *model kind*; "type" is only a column's SQL type): `kind` is the kind's name, with that kind's settings beneath it and exactly one key (`kind: {incremental_by_unique_key: {unique_key: [id]}}`, or block style), or a plain value for a kind with no settings (`kind: view`, `kind: full`, `kind: mapped`). A setting of another kind is an unknown key; two kinds, an empty `kind` or a list is DDB-248. A `kind` from a folder's `defaults:` is replaced whole by the model's own, never merged key by key. The form `kind: {type: full}` of the first releases is not read (DDB-248 says what to write). `view` is DDL only; `full` reloads everything; `incremental_by_unique_key` upserts by key; `incremental_by_time_range` loads slices after `MAX(time_column)` minus `lookback` (needs `time_column`, a DATE or TIMESTAMP). Other load shapes (a backfill, a merge) are named operations under `loads:`; see `schemas/model.schema.json` next to this file.
- **Types**: declare exact types. Types with no faithful equivalent are refused (HUGEINT, unsigned integers, structs, lists). A bare `VARCHAR` is unlimited text (`nvarchar(max)` on SQL Server, `text` on PostgreSQL) and stays unlimited from source to output unless a length is declared or written (`CAST(x AS VARCHAR(n))`). `sum(int)` is HUGEINT in DuckDB, so write `CAST(sum(x) AS BIGINT)`.
- **Strings** follow the project's profile (`string_semantics` in `dbdatabuild.yml`): by default case-insensitive, accent-sensitive, trailing spaces ignored. Every engine in use needs a collation in config (DDB-312). Do not rely on a comparison that the profile does not promise.
- **What cannot be written** (DDB-324, the message names the construct): `UNNEST`, list and struct constructors, `USING SAMPLE`, `x op ANY/ALL (subquery)`, row-value `IN`, a window partitioned by a correlated value, date or timestamp series. A `DISTINCT ON` is accepted only when its ORDER BY includes the declared grain of every table it reads. `GROUP BY 1`, `GROUP BY ALL`, `USING`, `NATURAL JOIN`, `SELECT *` and macros are fine: DuckDB expands them before the tool looks at the query. `generate_series` and `range` work over integers only. A `VALUES` list works (inline or as `(VALUES ...) AS t(a, b)`) when its columns are BOOLEAN, SMALLINT, INTEGER, BIGINT, DECIMAL, DOUBLE, FLOAT, VARCHAR, DATE or TIMESTAMP and its cells do not read another table; any other column type (TINYINT, unsigned and 128-bit integers, TIME, intervals, lists) is refused, so cast the cells.
- **The tool rewrites a few things for the engines** (`length` trailing spaces, `round` of a double, `TRY_CAST` of a string, integer `sum`): you write the DuckDB meaning and the rendered scripts compute the same. `dbdatabuild help matrix` lists what still differs (for example `TRY_CAST('12.7' AS INTEGER)` is 13 in DuckDB and NULL on the engines).
- **Indexes and keys**: a merge on a key never needs an index or constraint, but a key without an index scans the table on every load (DDB-223). Whether a key is enforced as unique is the person's choice; declare `unique: true` only if they want it. `lint_ignore: [DDB-223]` silences advice for a model.
- **Macros** (`macros/*.sql`, DuckDB `CREATE MACRO name(args) AS expr` or `AS TABLE SELECT ...`, `CREATE TYPE`, several to a file separated by `;`, nothing else) reuse structure without copying it. DuckDB expands them while the model is lowered, so each model's rendered SQL is for the table it was given: `query_table(tbl)` takes a table name as a constant string, `COLUMNS(lambda c: c = col)` a column name, and `CASE WHEN col IS NULL THEN ... ELSE ... END` over such an argument is folded to the branch taken (a live table and its snapshot are one macro: `snapshot_at('snap.orders', 'snap_date')` and `snapshot_at('live.orders', NULL)`). Arguments must be constants (a name cannot come from a column); a macro may call another that is defined before it in dependency order but not itself. A model that calls a macro depends on it and on the tables it reads (shown by `graph` and `metadata`). A parameter of type `NAME` (`table: { type: NAME, value: src.orders_snap }`, empty is NULL) is written into the call as the string it names, per connection, so `snapshot_at(${connection.table}, ${connection.date_col})` is the query for that connection's table; a model whose names differ between connections gets one lowered file per distinct query.
- **Strings on two engines**: SQL Server ignores trailing spaces in a comparison and PostgreSQL keeps them, so a project on both sets `string_semantics` per connection (`connections.<name>.string_semantics`). A model that compares, joins, groups or deduplicates string columns on connections that disagree gets DDB-236; a column that never ends in a space is declared `trimmed: true` (`check` counts the rows that break it, DDB-237), or the model says `lint_ignore: [DDB-236]`. `sample` and `test` run a model the way its first connection compares strings (the profile's DuckDB collation, and `rtrim()` where trailing spaces are ignored), and `sample` says so.
- **Hooks** (`hooks:` per model, `hook_groups:` in config) are native SQL files run before or after plan steps (`pre_`/`post_` `create`, `alter`, `load`, `backfill`). They run exactly as committed, so treat a new one as risky.

## Project tests

`tests/metadata/<name>.sql` is a rule: one DuckDB SELECT over the `metadata_*` views that returns the violations (no rows = pass). Put settings in comments at the top: `-- description: ...`, `-- severity: error|warning`, `-- tags: a, b`. Views: `metadata_columns` (the columns of every model, native types per target, `model_kind`), `metadata_models` (every model of the seven kinds, with `kind`, `title`, `description`, `tags`), `metadata_info` (title, description, tags and properties of every object, one row each), `metadata_upstream` (with `upstream_category`: `model`, `macro` or `unknown`, and `upstream_kind`: the model kind of a model, null otherwise), `metadata_lineage`, `metadata_native_types`, `metadata_indexes`, `metadata_foreign_keys`, `metadata_loads`, `metadata_hooks`, `metadata_index_advice`, `metadata_current` (the raw JSON documents; `subject_kind` is `project`, `model` or `plan`, `model_kind` the model kind). Run `test --format json`; a failing error-severity rule is DDB-601, a rule that cannot run DDB-602. Do not weaken or delete a rule to make a model pass without asking the person.

`tests/models/<model>.yml` tests a model's logic on rows you give it (the file name is the model name; settings are `# description:`, `# severity:`, `# tags:` comments at the top):

```yaml
cases:
  - name: keeps null amounts
    given:
      staging.orders:                 # each table the query reads (mapped models and other models); unlisted tables are empty
        - {order_id: 1, amount: 10.00}
        - {order_id: 2, amount: null}   # a plain null is NULL; "null" in quotes is text; a column left out is NULL
    expect:                           # rows the query must return (cast to the declared types); {rows: [...], ordered: true} to check order
      - {order_id: 1, amount: 10.00}
      - {order_id: 2, amount: null}
    assert: SELECT * FROM result WHERE amount < 0    # optional: violations over the table `result`
```

`project tests run --kind model` runs them in DuckDB (the query as written, no target). A failure shows `_diff` rows (`missing` or `unexpected`). Write the expected rows from what the model *should* do, not by copying its output: a test copied from the output cannot fail.

## Reading a plan

`connection deploy --write-plan --format json` returns `data.plan.steps`. Each step has `type` (`ddl`, `load`, `backfill`, `hook`, `track`), `risk` (`safe`, `risky`, `destructive`), `reasons`, the exact `text`, and for loads the `parameters` and resolver result. Summarize for the person: what is created, altered or dropped, what loads, and every risky or destructive step with its reason. `apply` needs `--allow-risky` for risky steps and `--allow-destructive <object>` for each object with a destructive step; never add those flags yourself. A step that has computed `inputs` shows each with its value and source. If an apply stops with DDB-454 (a computed input is not what the plan was made with), report each moved input with its planned and new value and ask; do not add the printed `--input` overrides, which are the person's yes, without their go-ahead, and never use `--yes` for it.

## Facts to keep straight

- DuckDB SQL is what you write; the target SQL is generated. Never write T-SQL or PostgreSQL syntax in a model.
- A change to an incremental model's query blocks the next plan (DDB-431) until a person plans again or accepts it with `connection deploy --ack definition:<model> --reason ...`. A refresh runs what `project compile` wrote into `rendered/<connection>/loads.yml` (every load) and `rendered/<connection>/refresh/<plan>.yml` (the members of a plan); it never plans, and with the default check (`objects`) it stops when a table is behind the model (DDB-447). A change someone made in the database blocks that object (DDB-430) until `ack drift` or a restore.
- `lowering: { enabled: false }`, `lint: { indexes: false }` and `rewrites: { fidelity: native }` in `dbdatabuild.yml` switch features off for the whole project (the last one gives each engine's own behavior where it differs from DuckDB, for shorter queries: `dbdatabuild help matrix --rewrites` says what changes): ask before changing config.
- The human interfaces are `dbdatabuild ui terminal` (terminal) and `dbdatabuild ui web` (a page: health, lineage, models with their lowered and rendered scripts, plans and their questions, sample data, table diff, tests, the matrix; it applies a plan only if started with `--allow-apply`, on the person's confirmation); they run the same commands. You do not need them, but you may tell the person about them.
- Anything not covered here: the `schemas/` folder next to this file has the exact shape of every file and every command's output, and `dbdatabuild help code <code>` explains every diagnostic.
