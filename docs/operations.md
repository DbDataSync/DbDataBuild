# Operations guide

For the people who run `dbdatabuild` against a real database: what it needs, what it does, how to schedule it, and what to do when something goes wrong. Everything here was checked against the behavior of the tool on SQL Server 2022 and PostgreSQL 17. **Fabric has not been run against a real engine**, so nothing here is claimed for it.

## 1. Install

`scripts/publish.sh <rid>` produces one file, `publish/<rid>/dbdatabuild` (`.exe` on Windows; about 200 MB: the .NET runtime, the tool, the polyglot SQL library and DuckDB). Copy it anywhere; nothing else needs installing. On first start the runtime unpacks the native libraries into `$DOTNET_BUNDLE_EXTRACT_BASE_DIR` (default `~/.net`, `%TEMP%\.net` on Windows); on a locked-down host point that variable at a writable directory.

- **linux-x64**: built and tested (unit and real-engine suites).
- **win-x64**: builds from Linux (`TARGET_RID=win-x64 scripts/build-polyglot.sh` cross-compiles the SQL library with MinGW, then `scripts/publish.sh win-x64`). The Windows build has been run only under Wine (every offline command gave byte-identical output and identical rendered files to Linux, and the unit suite was run there; see `docs/progress/state-and-apply.md` entry 34). It has **not** been run on real Windows, the single-file form could not be run under Wine (a Wine limitation with single-file .NET), and the terminal interface has not been tried on a Windows console.
- Other platforms are not built.

## 2. Connections and logins

A **connection** is a named database endpoint: an engine (`sqlserver`, `postgres`, `fabric`; or, for a system the tool only reads, `readonly duckdb`, `readonly odbc`, `readonly flightsql`) and optionally its version, declared under `connections:` in `dbdatabuild.yml`. A connection named after an engine (`sqlserver`) exists without being declared. Two servers of one engine are two connections (`warehouse_new`, `warehouse_old`), each with its own login and its own version, so each gets the rewrites its engine version needs.

Connection strings come from environment variables, never from files in the repository, one pair per connection (the name in capitals):

| Variable | Used by | Needs |
|---|---|---|
| `DBDATABUILD_<CONNECTION>_READ` | `connection status`, `connection deploy` (planning), `connection monitor`, `connection compare`, `project import`, the read side of applying a plan, and, for a copy, the origin connection's read | catalog and tracking-table read; a select on the origin's tables |
| `DBDATABUILD_<CONNECTION>_WRITE` | `connection init --apply`, `connection deploy` (applying a plan, `--ack`), `connection refresh`, `connection publish`, `connection seed --apply` | DDL and DML in the managed schema names, and insert/update on the tracking tables |

**`readonly` connections.** A system the tool must only read says so: `shop: { engine: readonly postgres }`. No `_WRITE` login is read for it (do not set one), and the tool refuses it as a destination of a model or a copy, as `tracking.connection`, and as the connection of `deploy`, `refresh`, `seed`, `publish`, `init` and `ack` (DDB-455). It is an origin: a copy, a mapped or native model, a `source` resolver; `connection inspect`, `status`, `monitor`, `compare` and `project import` read it. `readonly` is a promise of the tool; the account's own rights are the guarantee, so give the read login `SELECT` only. **A DuckDB file** is read the same way: `analytics: { engine: readonly duckdb }`, and the login `DBDATABUILD_ANALYTICS_READ` is the **path of the `.duckdb` file** on the machine that runs the tool (opened read-only; a file that is not there is an error and is never created; the path is never printed) or `:memory:` (a database with no file, for a native query that reads a Parquet or CSV file: `SELECT id, label FROM read_parquet(${project.file}) WHERE id >= ${project.min_id}`, the file name a parameter that is bound, not written into the text). A copy, a mapped model (`project import analytics 'src.*' --write`), a native query, a `source` resolver and `connection inspect` all work on it; `connection compare` does not. The file may be written by someone else between runs (a copy reads what is there when it runs), but not while a run reads it if they open it read-write: DuckDB lets one process write or many read. **An ODBC source** is any database with an ODBC driver: `legacy: { engine: readonly odbc }` (the dialect is `ansi`; `readonly odbc my_dialect` names a dialect of your own, `readonly odbc postgres` a built-in one). The login `DBDATABUILD_LEGACY_READ` is an **ODBC connection string** (`Driver={PostgreSQL Unicode};Server=db.internal;Port=5432;Database=erp;UID=reader;PWD=...`) or a **DSN** with its credentials (`DSN=erp;UID=reader;PWD=...`; a bare name `erp` is read as `DSN=erp`). It is never printed: a header shows the variable and the user (`UID`), and a failure shows the exception type and the error code, or, for a missing driver manager or driver, a sentence that says which. A copy, a mapped model (`project import`), a native query, a `source` resolver, `connection inspect` and a refresh all work on it, with the values bound by position (`?`; a value used twice is passed twice, in the order the plan records). The tool reads the tables and columns through `information_schema` when the dialect says `catalog: information_schema` (the default); for a system without it (a text or Excel driver, Access, an old database), a dialect with `catalog: odbc` reads the tables, columns, primary and foreign keys and indexes with the driver's own catalog functions (`SQLTables`, `SQLColumns`, `SQLPrimaryKeys`, `SQLForeignKeys`, `SQLStatistics`; a driver that does not implement one is said to lack it and that part is declared by hand), and a dialect with `catalog: none` makes `project import` say so and the structure check of a copy is skipped with a note, and the tool does not guess a table. `project import` writes the indexes of an ODBC source (from the driver's statistics), of a DuckDB file and of the engines; it says in words where an origin has none to read (a Flight SQL server has no call for them). With `catalog: odbc` a column is typed by the driver's type name if the dialect's `types:` has it, else by the standard name of its ODBC type code, so `bytea` or a boolean that psqlodbc reports as text need a line under `types:` (the dialects `postgres` and `sqlserver` have the usual ones). Types the standard names do not cover (`bytea`, `tinyint`...) are mapped under the dialect's `types:`. Timeouts are asked of the driver through ODBC (the statement's timeout: 30 seconds for a catalog read, a resolver's own limit for a `source` resolver, none for a copy's read; and a login timeout of 30 seconds), so a driver that ignores them ignores them here; `max_parallel` on the connection caps the sessions a refresh opens there, as for any origin. Put driver options in the connection string: psqlodbc hands a boolean over as text unless `BoolsAsChar=0` (the tool reads `t`/`f` too). `dialects:` in `dbdatabuild.yml` describes the SQL of a system (`quote`, `parameters`, `ping`, `catalog`, `identifier_case`, `limit`, `types`), with `ansi` as the default. A Flight SQL server is `engine: readonly flightsql [dialect]` (below). `dbdatabuild help dialects` prints the fields of a profile, the built-ins and an example.

**ODBC setup.** The tool ships neither an ODBC driver manager nor a driver: install both on the machine that runs it. When one is missing, `connection inspect` and a copy's check of its origin say which (`the ODBC driver manager is not installed on this machine`, or `the ODBC driver named in the login is not installed or could not be loaded`, or `...driver or data source ... was not found`), and the copy ends `failed: origin` without touching the table.

* **Linux.** Install unixODBC and the vendor's driver, for example `apt install unixodbc odbc-postgresql` (Debian, Ubuntu), `dnf install unixODBC postgresql-odbc` (Fedora, RHEL), or the vendor's package (Microsoft's `msodbcsql18` for SQL Server). `odbcinst -q -d` lists the installed drivers and `odbcinst -j` where `odbcinst.ini` is; a connection string may name the driver by that name (`Driver={PostgreSQL Unicode}`) or by the path of its library (`Driver={/usr/lib/x86_64-linux-gnu/odbc/psqlodbcw.so}`). Without root, unpack the packages into your own directory (`scripts/fetch-psqlodbc.sh` does it for psqlodbc, which is what the tests use), put its library directory on `LD_LIBRARY_PATH` and name the driver by path; the library `libodbc.so.2` of unixODBC must be on the machine.
* **macOS.** `brew install unixodbc`, then the vendor's driver (`brew install psqlodbc`); `odbcinst -j` shows the files. The tool loads the manager's library (`libodbc.2.dylib`); if it is not found, put the directory Homebrew installed it in on `DYLD_LIBRARY_PATH`. (Not tried on macOS.)
* **Windows.** The driver manager is part of Windows. Install the vendor's driver (for 64-bit tool, the 64-bit driver; "ODBC Data Sources (64-bit)" lists them) and use its name in `Driver={...}` or a DSN defined there.
* The driver decides the rest: transactions and snapshots (a copy reads what the origin gives a SELECT; nothing is held across the tables of a run), the types it reports, and its own options. The account's rights are the real guarantee that nothing is written.

**Flight SQL setup.** `engine: readonly flightsql [dialect]` reads an Arrow Flight SQL server (the owner's query proxy, Dremio, a DuckDB or SQLite Flight SQL server, ...). The tool ships its client; nothing else is installed. The read login `DBDATABUILD_<NAME>_READ` is a URI with options separated by `;`, written like an ODBC connection string (a value in braces `{...}` may hold `;` and `=`, `}}` is a `}`):

```
grpc+tls://proxy.example.com:31337;token=eyJ...                       # a bearer token
grpc+tls://proxy.example.com:31337;user=reader;password={p;w}         # user and password: the server's basic handshake trades them for a bearer token
grpc://127.0.0.1:31337                                                # no credentials, no TLS
grpc+tls://proxy.example.com:31337;token_env=PROXY_TOKEN              # the token is in this environment variable
grpc+tls://proxy.example.com:31337;token_command={az account get-access-token --resource api://proxy --query accessToken -o tsv}
```

* Schemes: `grpc` and `grpc+tcp` (no TLS), `grpc+tls`. The port is required. No path, query or user in the URI.
* At most one way to sign in: `token`, `token_env`, `token_command`, or `user` with `password`. None means the server is called without credentials. Other options: `tls_skip_verify=true` (no certificate check; TLS only), `ca_file=/path/ca.pem` (trust this authority instead of the machine's; the certificate must carry the host name used in the URI), `header.<name>=<value>` (a header sent with every call, for a proxy that routes on one).
* **Entra ID / OIDC.** The tool does not run an interactive login or an OIDC flow. Get the token outside the tool and give it to the tool one of three ways: `token=` (a token you obtained), `token_env=` (the name of an environment variable that holds it), or `token_command=` (a program the tool runs each time it connects, which must print the token alone and exit 0; it is started directly, not through a shell, with a 60 second limit; on Windows name an executable, or `cmd /c ...` for a `.cmd`). `az account get-access-token ... -o tsv` and `kubectl`/`gcloud` style commands fit. A token that expires during a long copy is not renewed until the next connection.
* The dialect is `ansi` unless one is named: positional `?` parameters, `"` quoting, `SELECT 1` as the ping. The dialect is the one of the system behind the connection: `readonly flightsql postgres` or `readonly flightsql sqlserver` for a proxy in front of those (with `positional` parameters, whatever the dialect says on the engines themselves), and a system with no built-in gets a profile named after it under `dialects:` (`readonly flightsql clickhouse_sql`). **A proxy is several connections**: when it chooses the system behind a call by a header (the owner's DbDataProxy reads `x-datasource`), each system is a connection of its own with its own login, `grpc+tls://proxy:8815;token_env=PROXY_TOKEN;header.x-datasource=erp`, and its own dialect. `dbdatabuild help dialects` has the example. A statement with parameters is **prepared** and its values are bound as typed Arrow values in the order the plan gives (a placeholder used twice is passed twice). A server that binds every parameter as text (voltrondata/sqlflite does) cannot compare a typed column with a bound watermark: cast in a native query (`CAST(${project.since} AS DATE)`).
* **The dialect.** With no dialect keyword in `engine`, run `dbdatabuild project update`: it asks the server (`GetSqlInfo`: its name and version, how it quotes identifiers), maps the answer to a dialect and commits it in `dialects.lock.yml` (commit that file: compile and the plans read it and stay offline). A keyword in `engine` always wins. A deploy or refresh asks the server again before an origin's turn and fails the origin, naming the difference, if it now reports another dialect; run `project update`, review the change to the file and compile again. `project update --check` is the CI form (writes nothing, exits 1 if anything would change); `--offline` reads no connection.
* The catalog (`project import`, the structure check of a copy, `connection inspect`) is read with the server's Flight SQL metadata calls first (schemas, tables with their Arrow schemas, primary keys, imported keys), then through `information_schema` as the dialect says (a server that answers neither the metadata calls nor `information_schema` has no catalog to read; the owner's proxy answers schemas, tables with their Arrow schemas and primary keys, not foreign keys, so those come from `information_schema` when the system behind it has one); with `catalog: none`, or on a server that offers neither, the tool says so plainly and the tables are declared by hand. An Arrow schema may mark every column nullable, so the structure check of a Flight SQL origin does not hold a declared NOT NULL against it.
* The command timeout is the call's gRPC deadline (30 seconds by default for catalog and resolver queries; a copy's read has none). Only endpoints on the same connection are read (a server that redirects to other hosts is not followed). `max_parallel` limits sessions as for any origin.
* Nothing of the value is printed: the header shows `host:port` and the kind of sign-in, a failure is named by gRPC status (`the Flight SQL server could not be reached`, `refused the credentials`, `the TLS handshake ... failed`, `did not answer in time`) and never repeats the server's text. A copy whose origin fails ends `failed: origin`.

There is no fallback from one login to the other, or from one connection to another: a missing variable is an error that names it. Every command prints which variable and which user it used (never the password). Use two separate accounts; the read account should not be able to write at all.

**Tracking** is a setting: `tracking: { connection: audit }` says which connection keeps the records of what the tool built for every connection it writes to (its read and write logins are used), and the tracking connection can be another one than the data's. With no `tracking:` the tool warns (DDB-232) and records nothing; `tracking: none` chooses that. Run `dbdatabuild connection init <tracking connection> --apply` once.

**Moving data between connections** is a copy: a model of `kind: {copy: {from: schema_name.table_name}}` on the destination connection, read from a model or a mapped model on the origin (a mapped model is `kind: mapped`: a table that exists and that the tool does not build; `dbdatabuild project import` writes them from a connection's catalog). Applying a plan that contains a copy needs the origin's read login as well as the destination's. A copy of one application's table on several connections (`connections=: [store_017, store_018]`) uses a `slice` so each origin's rows are kept apart and a run replaces only its own.

The `project` commands, `help` and `ui` connect to nothing themselves; the `connection` commands are the ones that open a database.

## 3. The normal cycle

1. `dbdatabuild project compile` and `dbdatabuild project compile --check` in CI. The first reads models and sources, lowers each query with DuckDB, and lints it per target; the second fails when the committed `rendered/` files differ from a fresh render. Run `dbdatabuild project compile` and commit the result when a model changes.
2. `dbdatabuild connection status` (read-only) shows drift: objects whose live shape no longer matches what the tool last recorded.
3. `dbdatabuild connection deploy` writes `plans/<connection>/<id>.plan.yml` (add `--write-plan` to stop there; without it the plan is shown and you are asked whether to apply it). Commit the plan. The plan records every statement, its risk class and a SHA-256 of its own content; **applying refuses a plan that was edited by hand**.
4. `dbdatabuild connection deploy --apply-plan <plan>` runs exactly the recorded statements (a plan that stopped part-way continues; a completed one is refused). `--dry-run` runs every check and prints every statement without executing anything. Risky steps need `--allow-risky`; destructive steps need `--allow-destructive <object>` for each object. `--allow-dirty` permits a working tree with uncommitted changes (recorded).
5. `dbdatabuild project show refresh [plan]` shows what a plan runs and what each load waits for (the dependency graph `project compile` writes into `loads.yml`). `dbdatabuild connection refresh [connection] [plan]` runs the loads of a **refresh plan** (`hourly`, `daily`; `default` when none is named) that `project compile` wrote (`rendered/<connection>/refresh/<plan>.yml`, with every load of the connection in `rendered/<connection>/loads.yml`, both committed): it reads those files and the scripts they name, not the models, checks what `refresh.check` says (default `objects`: each object it loads against the shape last deployed, from the tracking tables only), runs the loads as an event of its own that records the plan, its hash, the selection and the inputs each load ran with, and never changes structure. Plans are declared in `dbdatabuild.yml` (`refresh: { plans: { hourly: { expected_every: 1h } } }`) and each model says which plans its loads are in (`refresh: { hourly: incremental, daily: { load: backfill, inputs: { days: 60 } } }`; a folder's `_dbdatabuild.yml` can put every model beneath it in a plan). A model with a default load and no `refresh:` is in `default`. A model whose load is not routine (a load whose inputs have no default and the plan gives none, a copy of a native model, a structure hook) is left out of the plan with the reason; a deploy handles it. A copy between connections is a load like any other: put it in `hourly` or `daily` and the refresh needs the read login of each of its origins (`DBDATABUILD_<ORIGIN>_READ`) as well as the destination's; an origin that does not answer fails the copy (`failed: origin`; each origin is checked just before its own transfer, so the origins before it stay loaded) and the plan's `on_failure` decides about what reads the table. A copy that has to re-read an origin in full declares a second load (`loads: { default: {...}, full: { strategy: full_replace } }`) that a plan names (`weekly: { load: full }`) or a person runs (`connection refresh <connection> <copy>.full`). With `--parallel` above 1 the project is read for its graph; if it cannot be read the run goes one load at a time and says so (a line and a warning; `parallel_effective` in the JSON document). `connection refresh prod hourly --only-failed` runs only what the plan's last run left failed, skipped or not run. The plan's rules: `on_failure: stop | continue | ignore` (a membership can override it), `on_busy: skip | wait | fail` with `max_wait` (a lock per load; a busy skip is not a failure and what reads it still runs), `max_runtime` (plan, or a load's own), `expected_every` (`status` and `monitor` warn OVERDUE and SLOW and name the slowest load), `parallel` (how many loads may run at once, 1 to 64, default 1; `--parallel n` on the command wins). With `parallel` above 1 a load starts when the loads of the plan that it reads, and an earlier load of the same model, have ended; each running load uses a read and a write session of its own (about `2 x parallel + 2` sessions at the connection), a `stop` failure lets the loads in flight finish and starts none, and the results are still listed in the order of the plan (the `load n/m` progress lines are in start order). A dry run goes one load at a time. `max_parallel` on a connection (`connections: { shop: { engine: postgres, max_parallel: 2 } }`) is the most sessions one refresh opens there at once: at an origin the reads of a fan-in copy (so a shop's system is not flooded), at the destination a cap on `parallel`; it does not limit another process. The run ends `completed`, `completed_with_failures`, `stopped` or `failed`; anything but `completed` exits 1 with a line naming what failed and what was skipped. `connection refresh prod hourly tag:finance exclude:tag:slow` runs part of a plan (the event records the selection); `connection refresh prod sales.orders.backfill --input days=30` runs one load by itself, with an input given at the command. `project show refresh [plan]` reads the plans offline, `connection monitor prod hourly` shows a plan's runs (complete and partial apart) and `connection status` has a line per plan. This is the command to schedule. `--check none` asks the connection nothing about its structure; `--check live` compares each object with the catalog; `--on-fail warn` reports a failed check and runs anyway.

**Inputs and resolvers.** A load can compute its inputs (the window of a reload, a cut-off date) instead of taking them from a person: `inputs:` in the model, with `expression`, `target` or `source` resolvers (`docs/concepts.md`). In a refresh they are computed just before each load, on the clock of the day it runs (`timezone:` in `dbdatabuild.yml` or on a connection when the day should be a local one; UTC otherwise), and recorded in the event with their source and the resolver's hash. `connection refresh <plan> --dry-run` prints the values each load would use and `project show refresh <plan> --resolve` evaluates the expressions without a database. A resolver that fails (no row, two rows, NULL with `on_null: fail`, a value that does not fit the type) fails that load with `failed: input` and a message that names the input and the resolver; `--input <model>.<load>.<name>=<value>` gives the value by hand and the resolver is not run. In a deploy the inputs are computed when the plan is made and again when it is applied: if any moved (a window that depends on the date, across midnight) the apply stops with exit 1 before anything runs, prints both values and each override (`--input marts.fct.backfill.start=2026-02-27`); append them to the same command to apply with those values, or answer yes in an interactive apply. `--yes` does not approve them. A scheduler that applies plans should either pin the inputs when it plans (`connection deploy --write-plan --input ...`) or treat exit 1 with DDB-454 as "plan again".

**Engine behavior and speed.** By default the tool rewrites a query wherever an engine would answer differently from DuckDB (a trailing space not counted by `LEN`, an integer cut instead of rounded, a week counted another way), and those rewrites show in the rendered SQL. If you would rather have each engine's own behavior, for shorter queries and simpler plans, say so in `dbdatabuild.yml` (`rewrites: { fidelity: native }`, or `disable: [name]` for single ones) or in one model's definition. `dbdatabuild help matrix --rewrites` lists every rewrite, which ones an engine cannot do without (those stay on), and what the engine does when one is off; the rendered files say `-- rewrites off: ...`, and `project compile` reports the differences it no longer hides as notes.

## 4. Scheduling (SQL Agent, cron, any scheduler)

Schedule `dbdatabuild connection refresh` for routine loads; use `connection deploy` by hand or in a reviewed pipeline for anything that changes structure.

Exit codes: `0` ok, `1` findings (a diagnostic with an error severity, a refused plan, a failed step), `2` usage (a bad option, a missing file), `3` command not implemented, `70` internal error (a tool bug; please report it). A scheduler should treat anything but `0` as a failure. `--format json` prints one JSON document on standard output (shape in `schemas/output.schema.json`) with the data, the diagnostics and the human text; use it to feed monitoring.

SQL Agent job step (type: operating system command, run as a proxy account that holds the two connection strings in its environment):

```
dbdatabuild connection refresh sqlserver --project D:\etl\project --format json > D:\etl\logs\run.json
```

Make the working directory or `--project` a checkout of the repository: the tool reads the committed `rendered/` files and records the git commit with each plan.

**Housekeeping.** A refresh writes no plan file (the compiled plan is the plan); a deploy writes its plan under `plans/`. Every apply and every refresh writes a statement log (`.dbdatabuild/statement-log/`): measured for a run of 100 loads, about 2 MB. A job that runs every 15 minutes therefore leaves a few hundred megabytes a month. The tool deletes none of them yet (`retention.statement_logs_days` is read but not acted on): prune them from the scheduler (for example `find .dbdatabuild/statement-log -mtime +30 -type f -delete`), and keep the folder out of version control. Each refresh is one `ref-…` event in `migration_log` (with `lane = 'refresh'`), which does not hold the plan text unless `plans.refresh.audit` is `full`.

Only one deploy or refresh can work on a connection at a time: the tool takes an application lock (`sp_getapplock` on SQL Server, an advisory lock on PostgreSQL). A second run exits with a finding that says the lock is held; it does not wait. If a job overlaps its own previous run, that is the reason.

## 5. When something fails

- **Every statement the tool sends is written to `.dbdatabuild/statement-log/` before it is sent**, with its hash and step id, and the outcome after. If that log cannot be written the statement is not executed. It holds full statement text, so keep it out of version control (the repository's `.gitignore` excludes `.dbdatabuild/`) and ship it to your log store if you want it kept; it is the first thing to read.
- A failed step stops the plan and reports the **exception type and error number only**. Driver messages are not echoed because they can quote data (a conversion failure quotes the offending value). The error number and the statement log identify the failure; reproduce the query in the database to see the full message.
- **Stopping an apply**: the first Ctrl-C (or SIGINT) asks it to stop after the step that is running, so a statement that has started is finished and recorded, not cut off; the second ends the process at once. A stopped plan continues when the same plan is applied again. (The terminal and web interfaces have their own stop button, with the same rule.)
- **Continuing**: `dbdatabuild connection deploy --apply-plan <plan>` on a plan that stopped part-way continues it, but only if the live objects are exactly in the intermediate state the log recorded (the steps that finished are skipped). Otherwise it refuses and says what differs. A plan that completed is refused: it is applied once.
- **Drift**: if someone changed an object outside the tool, `connection status` and `connection deploy` say so and block that object. Accept the change with `dbdatabuild connection deploy --ack drift:<object> --reason <why>` (recorded with your login), or restore the object. `--ack definition:<model> --reason ...` accepts a changed query for an incremental model whose already-loaded rows were produced by the old query. `--ack history:<model>.<column> --reason ...` silences a recorded backfill that never happened; the report keeps the fact.
- **The tracking tables** live under the schema name `dbdatabuild` (configurable as `tracking: { schema: ... }`; the key is called `schema` and holds a schema name) of the connection named by `tracking: { connection: ... }`, which can be another connection than the one the data is on: every record names the connection it is about, so one tracking connection can hold the records of many. With no `tracking:` nothing is recorded and the commands that would record warn; `tracking: none` chooses that. `dbdatabuild connection monitor` summarizes them: applied plans, DDL, loads, recorded shapes, and anything that started and never finished. `dbdatabuild connection init` is safe to re-run; without `--apply` it only prints the script for review.
- **Metadata**: `dbdatabuild connection publish` (or `metadata: { store_on_apply: true }` in `dbdatabuild.yml`) stores the metadata of the project, every mapped and native model and every other model as JSON in the tracking tables, readable through the views `metadata_current` (with `subject_kind`, `project`, `model` or `plan`, and `model_kind`, the kind of a model: `view`, `full`, `copy`, `mapped`, `native` and so on; a mapped or native model is a model like the others) and `metadata_columns` (one row per column of any model; `model_kind` says which sort), and the table `metadata_dependency` (what each model depends on, directly at depth 1 and through others at a greater depth: `SELECT depends_on FROM metadata_dependency WHERE subject = 'marts.fct_orders'`, or `WHERE depends_on = 'staging.orders'` for what depends on it; tracking layout 8, which `connection init --upgrade --apply` brings a layout 7 store to). Tracking layout 3 added the source documents: a target initialised by an older tool is refused (DDB-505) until `dbdatabuild connection init --apply` upgrades it, which only creates what is missing. Layout 6 added the table `object_info`: the `title`, `description`, `tags` and `properties` of the project, its connections, models, sources, columns and indexes, one row each, written by `publish` beside the documents (a layout 5 store needs `connection init --apply`, which creates the table); nothing is written into the deployed objects themselves (DESIGN.md 6.5.8).
- **Comparing tables**: `dbdatabuild connection compare marts.fct_orders --against-schema dev_marts` (or `--against schema_name.table_name`, `--key a,b`) compares two tables of one target with the read login. It prints column and type differences, row counts, and how many rows are only on one side or differ, column by column, and reads no value; `--show-values [--limit n]` also prints sample keys and old/new values, and the smallest and largest of each column, to your terminal (or the JSON document) and nowhere else. Exit code 0 means identical. A comparison has no query time limit (the drivers' 30 seconds would stop it on a large table); `apply` statements have none either; reads that scan a table (resolvers, a range's bounds) wait ten minutes, catalog reads the driver's default. `--against-connection <connection>` compares with the same table on another connection, which may be another engine: each engine computes digests of the values and only digests are compared (floating-point columns are not compared; the digest query scans the whole table on each side). See DESIGN.md 9.10.
- **Choosing models**: `project compile`, `connection deploy`, `connection status`, `connection refresh`, `project sample`, `project show metadata`, `connection publish` and `project show graph` take selectors: `+model`, `model+`, `2+model`, `@model`, `kind:` (any of the seven model kinds, `kind:mapped` too), `connection:`, `tag:` (the `tags:` of a model's definition or of a `defaults:` section above it), `property:key=value` (the `properties:` the same way), `path:`, `changed:<git ref>` (a changed hook script, macro file, folder file, native text or rendered file counts for the models it reaches), `a,b` (both), `exclude:<selector>`. `dbdatabuild connection deploy changed:origin/main+` plans what a branch changed and everything that depends on it. `dbdatabuild project show graph` shows the graph (`--columns`, `--column model.column`, `--diagram dot|mermaid`); see DESIGN.md 9.9.
- **Gating**: `tests: { gate: { tags: [critical] } }` in `dbdatabuild.yml` makes `connection deploy` and `connection status` run the tests with those tags first and refuse when one fails (before the target is read); tests with other tags only advise.
- **Tests**: `dbdatabuild project tests run` runs the project's tests offline (nothing is contacted or written; `--kind metadata|model`, `--tag`, `--strict`). **Model tests** (`tests/models/<model>.yml`) give rows per table the model reads and the rows its query must return (`expect`, optionally `ordered`) or a query over `result` that returns violations (`assert`); they run in DuckDB, so they check the logic, not an engine. **Metadata rules** are in `tests/metadata/*.sql`: a DuckDB SELECT over the `metadata_*` views that returns the violations, with `-- severity: error|warning`, `-- tags: ...` and `-- description: ...` comments at the top. It exits 1 if an error-severity rule returns rows or cannot run (`--strict` also for warnings); `--tag` selects a group. Run it in CI next to `validate`, `define --check` and `render --check`; nothing else gates on it yet (DESIGN.md 9.8).
- **Mapped models**: `dbdatabuild project import [schema_name.table_name ...]` exports the tables and views a project reads but does not build, as mapped models, `models/<schema name>/<table>.yml` with `kind: mapped`, with the read login only (it needs no tracking tables). It shows a diff and writes nothing until `--write`; with no arguments it refreshes the descriptors the project has; `--check` fails (DDB-227) when one has gone stale, for CI. Columns whose type has no honest logical type (unlimited text, xml, json, arrays) are left out and reported (DDB-226): declare them by hand with a type you choose, and a refresh keeps them.

## 6. Who changed what: out-of-band DDL

The tool detects drift by hashing each object's catalog shape; it does **not** install triggers or event sessions and cannot say who changed something or what statement they ran. For that, configure the database's own audit:

- **SQL Server**: SQL Server Audit with a database audit specification on the managed schema names for `SCHEMA_OBJECT_CHANGE_GROUP` (and `DATABASE_OBJECT_CHANGE_GROUP`), writing to a file or the security log. The audit records the login, time and statement text. This is the authoritative record and is configured by the DBAs.
- **PostgreSQL**: set `log_statement = 'ddl'` (cheap, in the server log) or install `pgaudit` with `pgaudit.log = 'ddl'` for structured entries.
- **Fabric**: not checked.

Typical use: `dbdatabuild connection status` reports drift on `marts.fct`; the audit says which login ran the `ALTER TABLE`; the operator decides to acknowledge the drift (`--ack drift:<object>`) or to revert.

## 7. What the tool will not do

- Run any statement that is not in a plan, a tracking-table writer, or a recorded hook script.
- Drop an index it was not told about (an undeclared index is left alone and reported).
- Guess: a query it cannot lower (DDB-324), a type with no exact equivalent, or a construct the support matrix marks unsupported on the target is an error naming the model and the target. `dbdatabuild help code DDB-nnn` explains any code, and `dbdatabuild help matrix` prints what is known to differ per engine.

## 8. Large projects, and what was measured

Measured on local containers with generated projects (a Debug build; a release build is faster): `project compile` of 300 models about 9 s, of 1,500 views in a chain about 40 s; planning 300 models 12 s; applying a plan of 401 steps 9 s on PostgreSQL and 13 s on SQL Server; an incremental load by key of 2 million rows 4 to 10 s; `connection compare --against-connection` of 1 million rows 25 s and 5 million 110 s (SQL Server against PostgreSQL). Statements of an apply have no time limit; the reads that scan a table (resolvers, the bounds of a range) wait ten minutes; `connection compare` has no limit. A name longer than the engine keeps is refused before anything is planned (63 bytes on PostgreSQL, 128 characters on SQL Server, DDB-241). A refused login or a connection the server closed is DDB-242, with the driver's error number (18456, 28P01) and no driver message.
