# Progress log: state, safety, planning, apply (milestones 4 to 6)

Written as work proceeds, one entry per commit, so a reviewer can follow the decisions. The final review summary is `docs/progress/REVIEW.md` (written last).

## 1. Hashes and the tracking-table definition (`DbDataBuild.State`)

New offline project, no database drivers.

- `Hashing`: `ShapeHash`, `PhysicalHash`, `ScriptHash`, built from a canonical text (`shape/v1`, `physical/v1`) so a hash changes only when what it covers changes. Shape hash is sorted by column name and ignores column order (ordinals are recorded separately as `OrdinalText`). The definition hash is the existing `AstHasher`.
- Canonical text escapes `\`, `|`, newline and `~` (the null marker). **A test found a real collision here**: null and the literal text `~` hashed the same. Fixed before anything was recorded anywhere.
- `TrackingSchema`: the seven tracking tables as one logical definition. `TrackingDdl`: idempotent init scripts for SQL Server, Fabric (unverified) and PostgreSQL, one statement per step with a stable id (`init-00`...).

Deviations from the illustrative DDL in DESIGN.md 12 (the design says that DDL is illustrative):

| Deviation | Why |
|---|---|
| Log ids (`ddl_id`, `block_id`) are tool-generated GUIDs, not `IDENTITY` | `IDENTITY` differs across engines and is unconfirmed on Fabric. Order comes from the timestamps. |
| Added `tracking_version` table | Lets a later tool detect and migrate an older layout. |
| Added `interval_id` and primary keys on every table | Every table gets a key so each engine can create it without engine-specific options. Fabric keys are `NONCLUSTERED ... NOT ENFORCED`. |
| Fabric text types are `varchar`, not `nvarchar` | Fabric has no `NVARCHAR` (Microsoft T-SQL surface area page). Unverified: no Fabric engine has been available. |

Tests: `HashingTests` (every covered attribute changes the hash, collisions), `TrackingDdlTests` (idempotent, no DROP/ALTER/TRUNCATE, parses with ScriptDOM and polyglot, quoting).

## 2. Logins, the mutation gate, the statement log (`DbDataBuild.Execution`)

The only project that references a database driver (Microsoft.Data.SqlClient, Npgsql). Implements DESIGN.md 9.2 and 9.3.

- **Logins** (`LoginSettings`): connection strings come from environment variables `DBDATABUILD_<TARGET>_<READ|WRITE>`, for example `DBDATABUILD_SQLSERVER_WRITE`. There is **no fallback between logins**: a missing read login is DDB-501 even when a write login exists. The header description shows the variable and user, never the password.
- **`MutationGate`**: the one handle on a write connection. It takes only `GateStatement`s, checks the statement's kind (tracking, data, DDL) against what the running command permits (DDB-502), logs the statement **before** executing it, logs the outcome after, and does not execute when the log cannot be written (DDB-503). Dry-run mode does the same checks and log entries and executes nothing. `GateStatement` has no public constructor: plan steps come in through `FromPlanStep` (which refuses `Tracking`), tracking statements through an internal factory.
- **Statement log**: JSON lines, one file per run, flushed to disk per line. Failure outcomes record the exception type and driver error number, never the driver message (which can quote data, DESIGN.md 14.2).
- **`ReadSession` and `ReadGuard`**: read-only queries only. The guard allows a single SELECT/WITH, refuses data-changing keywords outside quotes and comments, and refuses dollar-quoting. Tests include quote-hiding tricks (`$$'$$; DROP TABLE x; --'`, backticks). While writing it I removed backtick handling, which would have let `` ` `` hide a statement from the scanner on PostgreSQL. The guard is a second layer: the read login's permissions are the real enforcement. PostgreSQL read sessions also set `default_transaction_read_only=on`.
- **Invariant test** (`GateInvariantTests`, DESIGN.md 9.3): a source scan that fails if any file other than `MutationGate.cs` and `ReadSession.cs` calls a command API, if any project but Execution references a driver package, or if a connection opener becomes public. Sensitivity checked by adding a file with `ExecuteNonQuery` (test fails). **Limitation**: it is a source scan, not a call-graph analysis; a determined reflection call would not be seen.
- New diagnostics DDB-501 to DDB-505 (state and safety).

Tests: `MutationGateTests`, `ReadGuardTests`, `GateInvariantTests`. Unit suite: 649 tests passing.

## 3. Catalog reader, tracking store, `init` command

- **`CatalogReader`** (read session): live shapes of the tables and views in a schema on SQL Server and PostgreSQL: columns (types without parameters, length in characters, precision, scale, nullability, collation, computed text) and physical items (indexes, SQL Server compression and partition counts). Lengths are normalized (`nvarchar(20)` is 40 bytes on SQL Server, reported as 20).
- **`Drift.Classify`** (State, pure): `Missing`, `Untracked` (ask to adopt), `InSync`, `OutOfBand` (block) from the live shape and the newest recorded shape hash. These are the object-level rows of the decision table in DESIGN.md 11.
- **`TrackingStore`**: `InitAsync` (through the gate), `StatusAsync` (missing / ready / unknown layout, DDB-505), `LatestShapeHashesAsync`, `RecordSchemaVersionAsync`. Timestamps come from `TrackingClock`, strictly increasing at millisecond precision, so two records for one object in the same millisecond still order. The values are UTC wall time with Kind Unspecified because the columns are zone-less and Npgsql refuses UTC-kind values for them (found by the PostgreSQL conformance test).
- **`dbdatabuild init`** (effect: tracking tables only): prints the idempotent script by default and connects to nothing; `--target` is needed when the project has more than one default target; `--apply` runs it on the write login through the gate and writes `.dbdatabuild/statement-log/` (now git-ignored). No fallback from read to write login. The generic internal-error text no longer says "no target statements ran"; it points to the statement log.

Real-engine tests (SQL Server 2022 and PostgreSQL 17): init and rerun, unknown layout version, shape and physical hashes change exactly when a column, length or index changes, schema-version round trip with drift classification, failure outcomes without driver text, PostgreSQL read sessions are read-only, and the `init --apply` command end to end with its statement log.

## 4. DDL generation and the type table (`DbDataBuild.Targets/Ddl`)

`ITarget.CreateDdl(config)` gives a `DdlGenerator` per engine (`TSqlDdl` for SQL Server and Fabric, `PostgresDdl`): logical type to native type, expected live shape per column, and the statements CREATE SCHEMA/TABLE, ADD/DROP/RENAME/ALTER COLUMN, DROP TABLE and CREATE OR ALTER VIEW (PostgreSQL: DROP VIEW then CREATE VIEW, because `CREATE OR REPLACE VIEW` cannot change columns).

Mapping choices (DESIGN.md has no table for these; this is the proposal for review):

| Logical | SQL Server | Fabric (unverified) | PostgreSQL |
|---|---|---|---|
| BIGINT / INTEGER / SMALLINT | bigint / int / smallint | same | bigint / integer / smallint |
| TINYINT | **smallint** (T-SQL tinyint is unsigned, DuckDB's is signed) | smallint | smallint |
| DOUBLE / FLOAT | float(53) / real | same | double precision / real |
| BOOLEAN | bit | bit | boolean |
| TIMESTAMP, TIME | datetime2(6), time(6) | same | timestamp(6), time(6) |
| TIMESTAMP WITH TIME ZONE | datetimeoffset(6) | same | timestamp(6) with time zone |
| DECIMAL(p, s), bare DECIMAL | decimal(p, s), decimal(18, 3) | same | numeric(p, s), numeric(18, 3) |
| VARCHAR(n) | nvarchar(n), nvarchar(max) above 4000 | varchar(n), varchar(max) above 8000 | varchar(n) |
| UUID, BLOB | uniqueidentifier, varbinary(max) | same | uuid, bytea |

Refused with DDB-321 (new): unsigned integers, HUGEINT, a VARCHAR without a length, DECIMAL beyond 38 digits, structs, lists, JSON. Text columns always carry the profile collation (`default` or the column's declared logical collation, from `string_semantics.collations`); a missing entry is DDB-312, and collation names are validated before they reach DDL text. Nothing is left to the database default, so the expected shape is known offline.

`DdlGenerator.Classify` grades a type change: none, widening (larger length or precision at the same scale, wider integer), or other. Widening is safe; other is destructive (DESIGN.md 10.4).

**Verified on real engines** (SQL Server 2022, PostgreSQL 17): for 20 columns covering every mapped type, the shape the generator predicts equals, attribute for attribute, what the catalog reader reports after CREATE TABLE. ADD, widening ALTER, NULL/NOT NULL ALTER, rename, drop, and a view created then replaced with different columns all run and change the shape as predicted. The PostgreSQL test image (alpine) has no `en_US.utf8`, so its tests use the `C` and `POSIX` collations.

Not done here: constraints and indexes from the model (`unique_key` does not create a unique constraint; the physical hash only tracks what exists). Noted for the plan's "noticed but not done" list.

## 5. The planner and the decision table (`DbDataBuild.Planning`)

`Planner.Plan(input, answers)` is a pure function: the project's models, a catalog snapshot, tracking records, committed rendered loads, resolver results and the answers so far go in; open **questions**, **blocks**, **skips**, **steps**, the answers used and "noticed but not done" items come out. It reads nothing and writes nothing, so every row is unit-tested without a database. The `plan` command (next entry) loops it with the question resolver until nothing is open.

- **Decision table as data** (`matrix/decision-table.yml`, embedded, 32 rows): each row has an owner (`planner`, `command` or `apply`), the model kinds it covers, a result, and for planner rows the name of the test that proves it. Every step names its row id first in its reason chain. A test fails on an unknown id, on a planner row without a real test, and on a duplicate id. Rows owned by `command` and `apply` (stale rendered files, out-of-sync definitions, stale plan, resolver drift) are listed so the table is complete; those checks are built in the commands.
- **Object level**: missing (create schema and table or view), untracked (question `Q-adopt-*`, answers `adopt` or `stop`), out of band (block DDB-430 unless a person acknowledged that exact shape), in sync.
- **Columns**: add (always asks the history question; NOT NULL is risky), drop (destructive), declared or answered rename (risky), type change graded by `DdlGenerator.Classify`, nullability and collation changes graded. Running shapes are tracked so every DDL step records the hash the table must have after it.
- **Loads**: the default operation's committed script becomes a load step (structure first, then loads, both in dependency order). Runtime parameters without a value are `Q-param-*` questions with the explicit options `provide` and `skip_load`; resolver results come in from the command; a NULL watermark follows the declared `on_null`; values are checked against their type and `max_span`. A table that does not exist yet is empty by definition, so its resolver is not consulted.
- **Blocks and skips**: an incremental model whose query changed since its last recorded load is blocked (DDB-431) until acknowledged; a blocked or skipped model skips everything that reads from it (DDB-433); a cycle plans nothing (DDB-221); an unmappable type blocks only that model (DDB-321).
- New codes DDB-222 and DDB-430 to DDB-434. Acknowledgements are keyed by code, object and the specific hash (`DDB-430|marts.fct|<shape hash>`), so a later, different change blocks again.

Decisions for review:
1. **Views** record the hash of the applied `CREATE OR ALTER VIEW` text (from `ddl_log`) and are altered when it differs. A view's column types are derived by the engine and cannot be predicted offline, so a view step has no expected shape hash; apply will check column names and record the live shape.
2. A plan with blocks is still generated for the models that are not blocked; blocks and skips are printed prominently and the command exits non-zero. The alternative (refuse any plan while a block exists) is one line to change.
3. Unique-key constraints and indexes are not created from the model; the plan says so under "noticed but not done" once the command builds that list.

## 6. The plan document

`PlanDocument.Serialize/Parse` and `PlanReport.Markdown` (Planning project). A plan is two renderings of one object (DESIGN.md 10.2): a machine-readable YAML that `apply` consumes and a Markdown report for people.

- Every string is a JSON-quoted scalar (valid YAML), so scripts with quotes, backslashes, `\r\n`, tabs and non-ASCII text round-trip byte for byte (tested). Files use `\n` always, so the hash does not depend on the platform.
- The file carries a SHA-256 over everything except the hash line. `Parse` recomputes it and also requires the file to be **exactly** what `Serialize` would write, so even a cosmetic edit (a comment, re-indentation) is refused, as is any unknown key, bad enum value, missing hash or changed statement. All of these are DDB-435.
- Plan id: the date plus the first 8 hex of a hash over the plan's content excluding id, commit and hash, so the same plan gets the same id and a different plan does not.
- The Markdown report shows each step's script, risk, reason chain, the answers that decided it (with notes and how they were given), parameters, resolver results, what needs `--allow-risky` / `--allow-destructive`, blocked and skipped models, and "noticed but NOT done".

Tests: `PlanDocumentTests` (round trip with awkward text, fixed point, tamper cases, unknown keys, id, report content).

## 7. `plan` and `check`

- **`TargetSnapshotReader`** (Execution, read session): live shapes of the managed schemas, existing schemas, the newest recorded shape hash per object (`schema_version`), the newest successful DDL statement hash per object (`ddl_log`, used for views), the newest successful load's definition hash per model (`run_log`), and acknowledged blocks (`block_log`). `RunResolverAsync` runs a committed resolver and requires exactly one row and one column.
- **`PlanningSession`** (Cli): the offline preflight, then the live side. The project must validate (the shared `ProjectChecks` of `validate`, plus `define --check` and a comparison of committed `rendered/` files with a fresh render), or nothing is planned (DDB-420, DDB-424, DDB-317 and friends, listed in the decision table as `command` rows). Then the tracking tables must be ready (DDB-505), the snapshot is read, and resolvers run for models whose table already exists.
- **`dbdatabuild plan`**: asks every open question (interactively, or from `--answers`; `--accept-inferred` takes only high-certainty proposals), re-plans until nothing is open, then writes `plans/<target>/<id>.plan.yml` and `.plan.md`. Blocks and skips are printed and the exit code is 1 when there are blocks; the plan is still written for the rest. The git commit and dirty flag are recorded; this tool's own `plans/` and `.dbdatabuild/` output does not count as dirty.
- **`dbdatabuild check`**: prints each object's state (missing, in sync, not tracked, CHANGED OUTSIDE THE TOOL), then what a plan would contain and ask. Writes nothing, asks nothing.
- `LoadRenderer` now also returns the rendered operations (script, resolver, parameters, watermark rule) so a plan does not re-parse manifests.

## 8. `apply`, `ack`, and the audit tables

- **`ApplyEngine`** (new project `DbDataBuild.Apply`): allowances (`--allow-risky`; `--allow-destructive <object>` naming each object, never "all"), then the read side (tracking ready, resume bookkeeping), then the **base check**: every object's state and hashes must equal what the plan recorded, and every resolver must return what it returned at plan time, or the plan is stale (DDB-437) and nothing runs. Then the application lock, then the steps.
- **Application lock**: `sp_getapplock` (session owner, no wait) on SQL Server, `pg_try_advisory_lock` on PostgreSQL, one lock per tracking schema. Taken and released through the gate and logged. A second apply gets DDB-439; the tool does not wait.
- **Per step** (all writes through the gate): DDL is logged in `ddl_log` before it runs (status `started`), executed, then the object's shape is re-read and compared with the hash the plan promised (DDB-441 on a mismatch, nothing after it runs), the log row is updated, and a `schema_version` row is recorded. A load writes `run_log` (parameters, definition hash, shape hashes, file hash) around the script. A track step records an adopted or acknowledged shape. `migration_log` gets a `started` row and a `completed` or `failed` row.
- **Failure**: the first failing step stops the run (DDB-440). After a failed statement the gate issues a rollback so tracking writes can still happen; a mutation test confirmed this matters on PostgreSQL (an aborted transaction otherwise rejects the failure record). Error text in logs and output is the exception type and driver error number only.
- **Resume**: `apply --resume` continues only when the finished steps are a prefix of the plan and each touched object is exactly in the state its last finished step promised; otherwise stale. Without `--resume`, a plan that started before is refused (DDB-438); a completed plan is never run again.
- **Dry run** runs the same preflight and the same code path through a gate that logs and executes nothing; it needs the read login only. A dirty working tree refuses a real apply (DDB-442, `--allow-dirty` records it) and only warns on a dry run.
- **`dbdatabuild ack drift <object>` / `ack definition <model>`** (effect: tracking tables only) record a person's decision with the exact hash it is about, who made it and why (`--reason` is required). It clears exactly that block: a later, different change blocks again. A repeated ack is a no-op.
- New codes DDB-436 to DDB-442.

**Verified on SQL Server 2022 and PostgreSQL 17** by one scenario per engine (`ApplyConformanceTests`): init, render, check, plan, dry run (nothing created), apply (data, views, and all four audit tables), a refused re-apply, a routine load, stale rendered files (DDB-424), an incremental definition block (DDB-431) with the downstream view skipped (DDB-433), `ack`, an unanswered history question (DDB-414) then the answered plan with the note carried into the report, an out-of-band column (DDB-430) then `ack drift`, a destructive step refused without its allowance (and with the wrong object), a stale plan (DDB-437), an edited plan (DDB-435), a load that fails because its source vanished (DDB-440, failure recorded) then `--resume` completing without repeating finished steps, and a competing application lock (DDB-439). Statement logs were checked for secrets.

Known gaps, listed for review: unique-key constraints and indexes are not created; resolver and operation choice is the default operation only (no `--operation`); no `backfill` or `hook` steps yet (milestone 7); views are verified by existence, not column names; `report` is not built; `run` (plan plus apply for routine loads) is not built; the live-catalog collation check in `check` is not built; the plan JSON Schema cannot verify the content hash.

## 9. `run` and `report`

- **`dbdatabuild run`** (effect: target data writes): plans like `plan`, and applies only if the plan is routine loads and nothing else: no open question, no block, no skip, and no step that is not a safe load. Otherwise it prints why, executes nothing, writes nothing, and points to `plan` (DESIGN.md 9.1). When it does run, the plan is written like any plan and applied through the same `apply` code, so the plan files, `migration_log` and the statement log all show it. `run` cannot ask questions; a load with an unanswered runtime parameter is not routine.
- **`dbdatabuild report`** (effect: target read-only): recent applied plans, DDL and loads (`--last N`), every object the tool has recorded with how many shapes and whether it is in sync now, and a "needs attention" list: plans that never completed, DDL or loads that did not finish ok, and objects changed outside the tool, each with the command that deals with it. Exit code 1 when something needs attention. The per-column history consistency report of DESIGN.md 12.3 is not built.

All thirteen commands in the command table now exist.

## 10. Operation choice, backfill, and `operation_interval`

- `plan --op model=operation` loads a model with a named non-default operation (a routine, safe load). `plan --backfill model=operation` plans that operation as a **backfill step**: type `backfill`, risk **risky** (so `apply` needs `--allow-risky`), and the model has no routine load in the same plan. Both are repeatable; a model named twice with different operations, an unknown model, or malformed `model=operation` is a usage error before anything is read. A named operation that is not rendered for the target blocks the model (DDB-434, decision-table row `load.operation.missing`). The resolver of the chosen operation, not only the default one, is run at plan time.
- Backfill parameters are questions like any other (`Q-param-<model>-<op>-<param>`), and `max_span` is enforced at plan time (DDB-412).
- `apply` records every load and backfill that has a range in `operation_interval`: `range_start` and `range_end` for a range operation, the watermark as `range_start` for a watermark load, the shape hash after the step, and the operation (`load` or `backfill`). This is the input the history consistency report of DESIGN.md 12.3 needs; that report is still not built.
- Decision: a backfill does **not** clear the "incremental model changed since its last load" block (DDB-431). DESIGN.md 11 says "require `ack` or explicit backfill"; a range backfill does not necessarily cover everything the old query loaded, so clearing the block needs a person's `ack definition`.
- Verified on both engines (`Operations_can_be_chosen_...`): a watermark load on a new table uses the declared initial literal and records its interval; usage errors; an operation that is not rendered; a range longer than `max_span` refused at plan time; a backfill refused without `--allow-risky`, then applied, replacing rows that had been changed in the target from the source, with its `operation_interval` and `run_log` rows.

## 11. Column history in `report` (DESIGN.md 12.3)

`ColumnHistory.Build` (Planning, pure) joins three things the audit tables already keep: the history answers embedded in each completed plan (read back from `migration_log.plan_text` with the same tamper-checking parser `apply` uses), the object's recorded shapes, and `operation_interval` joined to `run_log` for timing. For each column a plan added it reports when, which schema version, what the person decided (with the note, how it was answered, and who applied it), how many recorded load ranges predate the change (they hold NULL) and how many came after. A requested `backfill_later` with no later recorded backfill is flagged and appears under "needs attention" (exit code 1) until a backfill is recorded; a backfill recorded before the column existed does not count. A plan text that cannot be read back is reported, not skipped silently.

Limits: the "ranges before the change hold NULL" count is about recorded ranges only (a full-replace or key load records none); it says what the tool did, not what the data contains. The unacknowledged-inconsistency policy of 12.3 ("a warning or a block for downstream models, using lineage") is not built: it is reported, not enforced.

## 12. Live collation check in `check`

`CollationChecker.CheckLive` applies the profile check to what the catalog reports for each managed table (DESIGN.md 9.4). Text columns left on the default collation must satisfy the profile (DDB-310); a column on the database default (the catalog reports no name, as PostgreSQL does) is DDB-311 because it cannot be verified; declared exceptions and columns the model does not declare are skipped. A DDB-310 makes `check` exit 1. Unit tests cover each case; the end-to-end scenario's `check` runs stay clean on both engines. Not covered by a real-engine test of a *violating* live column: it would also be drift, which the scenario already exercises.

## 13. JSON Schema for plan files

`schemas/plan.schema.json` describes the plan file for editors and reviewers (every key, enum, hash shape, and the rule that a step's reason chain is non-empty). Tests check three things: what the writer produces satisfies it; structural damage (unknown key, bad step type, risk, target, state, short hash) fails both the schema and the parser; and a well-formed *content* edit passes the schema but is refused by the parser, which is the point: the schema cannot verify the content hash, so it is for editors and the hash is the guard.

## 14. Model syntax for indexes and hooks (decisions from the operator)

Operator decisions recorded here: **indexes are declared, never implied** (a table with no unique constraint can still merge on a column; engine enforcement is the operator's choice, and lint or generation features may suggest or create them later), and **hooks are an open structure**: ordered, named, per-event, per-target, with named groups.

```yaml
indexes:
  - {name: uq_fct_orders_key, columns: [order_id], unique: true}
  - {name: ix_fct_orders_date, columns: [order_date], include: [amount], targets: [sqlserver]}

hooks:                                   # an ordered list: this is the run order within an event
  - {name: grant_reader, event: post_create, script: hooks/grant_reader.sql}
  - name: refresh_stats
    event: post_load
    script: {sqlserver: hooks/sqlserver/stats.sql, postgres: hooks/postgres/stats.sql}   # one file per engine
    effect: data                         # ddl (default) or data; `run` runs only data hooks
    risk: safe                           # the author's declaration: safe (default), risky, destructive
  - {use: standard_audit}                # insert the hooks of a group, in place

# dbdatabuild.yml
hook_groups:
  standard_audit:
    - {name: stamp, event: post_load, script: hooks/audit_stamp.sql, targets: [sqlserver]}
```

- **Events are a registry** (`HookEvents`): `pre_` and `post_` times `create`, `alter`, `drop`, `load`, `backfill`. Adding a kind of hook is one row there plus the place in the planner that fires it. An event the planner does not fire yet (`pre_drop`, `post_drop`: there is no step that drops a whole object) is reserved and refused, so a hook never silently does nothing.
- **Groups** are defined once in `dbdatabuild.yml`, referenced with `use:`, expand in place, do not nest, and their hooks appear in plans as `group.name`. Names must be unique per model after expansion. A group can contain per-target scripts and `targets:` filters, so one group serves every engine.
- **Scripts** are project-relative `.sql` paths (no `..`, no absolute or drive paths, forward slashes); each holds native SQL for one engine and is executed exactly as committed. Validated by the loader, `schemas/model.schema.json` and `schemas/config.schema.json`, and through one conformance corpus (all new fixtures pass in both).
- `HookReader.Resolve(model, config, target, ...)` produces the ordered hooks for one target: groups expanded, other targets dropped, unknown groups and clashes reported once.

Not wired yet at this commit: planning, applying and offline validation of the scripts, index DDL, and index drift.

## 15. Declared indexes: catalog, DDL, planning, apply

- **Catalog** (`CatalogReader`): indexes are now read structurally (uniqueness, key columns in order with `desc`, included columns, and whether the index backs a PRIMARY KEY or UNIQUE constraint) on both engines, and turned into an engine-neutral canonical text `unique=<0|1>;keys=a,b;include=c` (`IndexText`). Plain indexes are physical items of kind `index`; constraint-backed ones are `constraint_index`. SQL Server compression items are kept.
- **DDL**: `CREATE [UNIQUE] INDEX name ON t (cols) [INCLUDE (cols)]` and drop (`DROP INDEX n ON t` on SQL Server, schema-qualified `DROP INDEX s.n` on PostgreSQL, whose index names live in the schema).
- **Planner** (rows `index.added`, `index.changed`, `index.unmanaged`, `index.unsupported`, `index.constraint_name`): a declared index missing on the table is created (safe) after the table's column steps; one that exists under the same name with a different definition is rebuilt (drop and create in one step, **risky**); an index that exists but is not declared is **never dropped** and is listed under "noticed but not done"; so is an index whose declaration was removed from the model. A declared index with the name of a PRIMARY KEY or UNIQUE constraint blocks the model (DDB-434). Fabric has no CREATE INDEX, so a declared index for it blocks (new DDB-322). A view cannot declare indexes. Constraint-backed indexes are never noticed. Index steps leave the shape hash alone, so their post-check is `expect: index:<name>=<canonical>` in the plan, verified against the live catalog at apply (DDB-441 on a mismatch).
- **Decision** (for review): the planner never drops an undeclared index. Dropping something an operator may have added on purpose is not something a model edit should do silently, and there is no way to tell a tool-created index from a DBA's. Removing an index is therefore a manual step, or a hook. If you want a `drop: true` or a `managed_indexes: exclusive` setting, it is a small addition.
- Verified on SQL Server 2022 and PostgreSQL 17 (`Declared_indexes_...`): creation, enforcement by the engine of a unique index, the catalog text of each, the rebuild refused without `--allow-risky` and then applied, an index added by someone else left alone and reported, removing a declaration not dropping anything, and physical differences not counting as drift.

## 16. Hooks in plans and applies

- **Where an event lands** (`Hooked` in the planner; the one place that says what each event wraps): `pre_`/`post_create` around the model's creation (the create step plus its indexes; schema creation is outside), `pre_`/`post_alter` around the changes to an existing object (column and index steps, `alter view`), `pre_`/`post_load` around the routine load, `pre_`/`post_backfill` around a backfill. Hooks of one event run in the order the model lists them (groups expanded in place). A hook whose event the plan does not reach (nothing to alter, no load rendered) does not appear. A blocked or skipped model runs none of its hooks. All structure (and its hooks) comes before all loads (and theirs), as for every plan.
- **Hook steps**: type `hook`, the script text exactly as read from the project, its hash, the event (in `operation`), the hook name (`group.name` for members), its `effect` (`ddl` or `data`) and a risk class from the author's `risk:` (default safe; a risky or destructive hook needs the usual `--allow-risky` / `--allow-destructive <object>` at apply). Reason chain starts with decision-table row `hook.fired`.
- **Checked before planning** (`HookLoader`, DDB-323, in `validate` and `plan`): the script exists inside the project, is not empty, parses with the target's offline validator (ScriptDOM or the PostgreSQL parser), and the event fits the model's kind (a view has no load or backfill). Unknown groups and name clashes after expansion come from the resolver.
- **Apply**: a hook runs through the gate as a DDL or data statement according to its effect and is logged in `run_log` (operation = event, `load_name` = hook name, the script's file hash). A failing hook stops the apply (DDB-440) and the plan resumes after it with `--resume`. A DDL hook that changes the object's shape is recorded as a `schema_version` row with source `hook`, so the operator's own change is not later mistaken for an outside change. The model should then declare what the hook adds, or every plan will reconcile it away (the planner treats the model as the truth); that interaction is the operator's to manage and is not hidden.
- **`run`** treats a safe data hook on `pre_load`/`post_load` as part of a routine load; any other hook makes the plan not routine and `run` refuses with the hook named.
- Verified on both engines (`Hooks_run_around_...`): per-engine scripts picked per target, a group from `dbdatabuild.yml`, order across create and load events, a dry run that shows scripts and runs none, `run` with data hooks, a ddl hook making `run` refuse, a missing script, a script that does not parse and an unknown group refused before planning, and a failing hook recorded as failed then resumed.

## 17. Acknowledging history warnings (`ack history`)

Operator's rule: history inconsistencies are information; the operator can make the warning go away without changing data and decides what is a continuing concern. New code DDB-443 (a warning, never a block).

## 18. Machine-readable output (`--format json`) and the `metadata` command

Operator decision: machine-readable output for as much metadata as the tool can generate.

- **Every command takes `--format text|json`** (a recursive option). In JSON mode standard output holds **exactly one document** and nothing else, with the same exit codes as text mode: `{schema: "dbdatabuild.output/1", command, tool_version, exit_code, ok, data, diagnostics, messages, errors}`. `diagnostics` are the structured form of what text mode prints on standard error (code, severity, title, location, found, supported, fix); `messages` and `errors` keep the human text, so nothing is lost; `data` is the command's payload. `schemas/output.schema.json` describes the envelope and every test validates against it. An unhandled failure is also a document (DDB-900, no stack trace, no data values). JSON mode never prompts: an open question is data (`open_questions`, with options and proposal) and the exit code is 1.
- **How it is built**: commands write to the two text writers they already had; `CommandReport` swaps them for capturing writers in JSON mode, `error.Diag(d)` replaces formatting a diagnostic by hand (35 call sites) and `output.Payload(key, value)` adds a part of `data`. Text mode is unchanged (one cosmetic difference: no blank line between diagnostics).
- **Payloads**: `validate` (counts, config, project and the full model metadata), `matrix` (every construct with status per target, version), `explain` (the descriptor), `loads` and `render` (operations, files with hashes, written/removed, out of date), `init` (every statement), `check` (objects with states and hashes, preview of steps, questions, blocks), `plan` (the whole plan object, files, answers, noticed, questions asked), `apply` and `run` (outcomes, dry-run statements, statement log, success), `report` (applied plans, DDL, loads, objects, column history with acknowledgements, needs attention), `ack` (what was recorded), `metadata` (below). Plans, answers and objects serialize straight from the same records the planner uses.
- **`dbdatabuild metadata`** (effect: offline only, `--format json` for the documents): per model `dbdatabuild.model/1`: kind, grain, targets, files, definition hash, upstream (marked model, source or unknown), per column the declared logical type, nullability, collation, the **native type per target** (or why it cannot be mapped), **lineage and inferred nullability** from the analyzer, expected shape hash per target, renames, every rendered operation with script and resolver hashes, matrix status, findings and parameters, declared indexes, and the resolved hooks per target with script hashes. The project document `dbdatabuild.project/1` has tool and matrix versions, the effective configuration (string semantics, collations, policy, hook groups) and every model with its hash. The planned `publish-metadata` stores exactly these documents in the target.
- Tested: unit tests per offline command (valid against the schema, payload keys, structured diagnostics, usage errors, internal failure document, text unchanged by default) and a run on both engines through init, check, plan, dry run, apply, a refused re-apply, an open question as data, and report.

## 19. Metadata stored in the target (`publish-metadata`, tracking layout 2)

Operator decision: the option to store all metadata as JSON in the target database for introspection.

- **Tracking layout version 2** adds `metadata_document` (kind, subject, `document` JSON, `document_hash`, recorded time, tool version, plan id, commit; append-only, key on kind, subject and time) and two views. The JSON column is `jsonb` on PostgreSQL and `nvarchar(max)` with an `ISJSON` check on SQL Server (`varchar(max)`, no check, on Fabric: unverified). `init` is idempotent and upgrades an older layout by creating what is missing and recording version 2; until then the tool says the layout is version 1 and to run `init` (DDB-505). Tested: a layout-1 database is refused, `init` upgrades it, then planning works.
- **Introspection views**: `metadata_current` (the latest document per kind and subject) and `metadata_columns` (one row per model column: logical type, nullability, collation, the native type for each target, inferred nullability and upstream lineage, unpacked with `OPENJSON` or `jsonb_array_elements`; not created on Fabric, where `OPENJSON` is unverified). - Verified on both engines: nothing stored until asked, one document per project and model, republishing writes nothing, the stored hash equals the one `metadata --format json` prints, the column view returns the native type per engine, a changed model writes its own document and the project document only, `store_on_apply` writes four documents after an apply, and the layout upgrade path.

## 20. Lowering is a stage of the tool

Operator decisions: the lowered query is a committed artifact; "cannot be lowered" is a hard error; the binder's rewrites are acceptable.

- **`DbDataBuild.Lowering`** (`PlanLowerer`): the C# port of the research prototype. DuckDB's plan comes from `QueryDescriber.SerializePlan` (offline, external access off, the query text a single string literal because `json_serialize_plan` rejects parameters; a second statement in it is rejected by the function). Differentially tested against DuckDB: every construct of the spike corpus either lowers to a query with the same rows and the same output names, or is refused by name (pinned list of eight), plus tests for window frames (ROWS versus RANGE, row by row with ties), null ordering, CTE order, literals, output types and every refusal.
- **Integration** (`ModelLowering`, `ProjectContext.RenderModel`): `validate`, `render`, `loads`, `plan` and `metadata` lower each model once (cached), lint and transpile the lowered query, and add the artifact `rendered/lowered/<model>/lowered.sql` to the rendered files, so `render --write/--check`, stale detection and removal of a deleted model's file work like every other generated file. Findings point at the artifact; views are transpiled from the lowered query too. `lowering: { enabled: false }` restores the old path. New code DDB-324; DuckDB's own parse errors stay DDB-306 and an undeclared table DDB-218.
- **Two things the end-to-end tests caught**: the plan does not carry the author's output names when no projection is at the top (a model with `AS size` came out as `col1` and the load failed), so names now come from `DESCRIBE` by position; and a duplicate name (a join of two `b` columns) is suffixed `_2`. Both are in the lowerer's differential test now.
- **Behavior on real engines**: with lowering on, all 69 real-engine tests pass, including a new one where `GROUP BY ALL` and `AVG` over integers produce on SQL Server and PostgreSQL exactly the 1.5 and 3.5 DuckDB computes (an integer-averaging engine says 1 and 3).
- **Tests changed because behavior improved**: eight unit tests that used `GROUP BY 1`, `GROUP BY ALL` and undeclared tables to provoke findings now use a construct lowering cannot fix on that engine (`REGEXP_MATCHES` on SQL Server 16) and declare their sources; they assert that lowering-off still reports the old finding.
- Unit tests 873, real-engine tests 69, all passing.

## 21. Subqueries are lowered

Operator decision: correlated subqueries are a hard requirement.

- **Method**: DuckDB's binder decorrelates every subquery (plan shapes in `docs/research/duckdb-plan-lowering/subq_probe.py`), so the lowerer re-correlates: a `DELIM_GET` column is the outer expression that feeds it (written as a `\u0002`-marked reference that is always qualified, whatever the outer block's own naming), the join back to the duplicate-eliminated values and the `GROUP BY` on them are dropped as constant per outer row, and the right side is printed as a nested query inside the outer block. `MARK` becomes `EXISTS (...)` or `x IN (...)` (null semantics preserved, so `NOT IN` against a set with NULLs behaves as in DuckDB), `SINGLE` becomes a scalar subquery, `INNER`/`LEFT` delim joins become `CROSS JOIN LATERAL` / `LEFT JOIN LATERAL ... ON TRUE`. DuckDB's guards are undone too: the single-row check of an uncorrelated scalar subquery, `count(*) = 1` over `LIMIT 1` for an uncorrelated `EXISTS`, the NULL guard around a correlated `count(*)`, and `row_number() <= k` partitioned by correlated values back into `ORDER BY ... LIMIT k`.
- **Scope rules**: the outer block is wrapped first when it cannot hold a subquery (DISTINCT, LIMIT, a set operation, a window), or when the subquery is correlated on an aggregate; an aggregate over an aggregate is wrapped.
- **Refused by name**: `x op ANY/ALL (...)`, row-value `IN`, a correlated subquery over a set operation, a window partitioned by a correlated value, a correlated `LIMIT` with an offset. A lowering whose text DuckDB itself would reject would be worse than a refusal, so every shape added was checked by executing the lowered text.
- **Tests**: 53 subquery forms (and the spike corpus, now with its lateral, `EXISTS` and `IN` cases lowering) lower to queries with the same rows and output names in DuckDB, including `NOT IN` with NULLs, zero-row scalars, nesting three deep, correlation through joins, `HAVING`, `ORDER BY`, `ON`, window `ORDER BY`, and a lowered text that reads like the original. Executed through polyglot on SQL Server 2022 and PostgreSQL 17: 51 and 52 of 53 match; the exceptions are SQL Server's rejection of an aggregate over a subquery and the spike database's case-insensitive collation. An end-to-end model with a correlated scalar subquery, a correlated `EXISTS` inside a `CASE` and a `NOT IN` is planned and applied on both engines with identical rows.
- **Found while doing it**: `BETWEEN` stays one node when its input is a subquery (now lowered); the virtual row-id column of a scan that selects no column; and the lowered text must qualify every inner column of a correlated block, because an unqualified `a` inside a subquery would silently bind to the inner table (a two-level case printed `(a = a)` before the fix).
- Unit tests 928, real-engine tests 71, all passing.

## 22. DISTINCT ON is lowered when its ordering decides the row

- `DISTINCT ON (k) ... ORDER BY k, o` becomes a derived table with `row_number() OVER (PARTITION BY k ORDER BY o) AS rn` filtered to `rn = 1`; the ON keys are removed from the window's ordering (they are constant within a partition). NULL keys form one group in both forms.
- **Why the guard**: DuckDB keeps an arbitrary row among ties and so does a window, so a tie would give different rows on different engines and could not be differentially tested. The ordering must therefore include the **declared grain of every table the query reads** (`ModelLowering` supplies the grain of each model and source). Refused, with the columns to add: an ORDER BY that omits part of the grain, no ORDER BY, an ORDER BY of only the ON columns, a derived table, a table without a declared grain. A join needs the grain of each side in the ordering.
- Found by the end-to-end test: when no projection sits at the top, the plan carries DuckDB's hidden trailing column (the DISTINCT ON key) and `DESCRIBE` names only the visible ones, so the lowered output is cut to the described columns (a regression test covers it).
- Tests: six deciding orderings (several keys, descending, NULLS FIRST, a filter, a join with both grains) give the same rows as DuckDB; six refusals; the lowered text; and a model planned and applied on SQL Server and PostgreSQL with identical rows (NULL as its own group, ties on the ON key resolved by the grain). Unit tests 942, real-engine tests 73.

## 23. Integer `generate_series` and `range` are lowered

- `generate_series(a, b[, s])`, `range(n)`, `range(a, b[, s])` over integer constants become `generate_series(start, stop[, step]) AS series(value)`; `range`'s exclusive end becomes an inclusive one (`range(2, 12, 5)` is `generate_series(2, 11, 5)`). The column is cast to BIGINT, DuckDB's type, because SQL Server's would be INT and arithmetic could overflow differently.
- **SQL Server quirk found on the real engine**: `GENERATE_SERIES` exists from SQL Server 2022 (version 16) but takes **no column alias list** (`AS series(s)` fails with "not a recognized function name"), and names its column `value`. The lowered query always names the column `value` (the author's name is the select alias), and the renderer drops `(value)` after `GENERATE_SERIES(...)` for the T-SQL dialects. PostgreSQL and DuckDB accept the list as written.
- Matrix: new row `fn.generate_series` (SQL Server `min_version: 16`, PostgreSQL native, Fabric unverified), with a spike corpus case. The conformance test is the evidence for the SQL Server and PostgreSQL claims; the spike has not been re-run with the new case.
- Refused (DDB-324, with the reason): date and timestamp series, a zero step, non-constant or NULL arguments, HUGEINT, other table functions, and `UNNEST` (lists have no equal on SQL Server; PostgreSQL's `unnest` would need list literals, which stay refused).
- Tests: 11 series forms (negative and zero-length series, a filter, a join to a table, `SELECT *`) give the same rows and names as DuckDB; the lowered text; refusals; a model with `range(0, 4)` left-joined to a table, planned and applied on SQL Server and PostgreSQL with identical rows. Unit tests 956, real-engine tests 75. Golden render files carry the new matrix hash.

## 24. Target rules, and `sum` widening

- New step between the lowered query and the transpile: `TargetRules` (DESIGN.md 7.6.1). It parses the DuckDB-dialect query with polyglot, rewrites recognised shapes with expression templates (written as DuckDB SQL, parsed once, with placeholders replaced by the original sub-trees), and regenerates DuckDB SQL. A query with no match is returned byte for byte, so nothing changes for existing projects unless a rule fires. Failure to print a rewritten tree is an exception, not a silent fallback (the first version of the decimal range check used `DECIMAL(60, 20)`, which polyglot refuses, and silently skipping would have hidden it).
- **Design decision**: marks, not type inference. The AST has no types, so the lowerer writes `round(CAST(x AS DOUBLE), n)` and `TRY_CAST(CAST(s AS VARCHAR) AS ...)` where it knows the types, and the rule recognises exactly that. `length` needs no mark.
- Rules: `length-trailing-spaces`, `round-double`, `try-cast-parse` (and the lowering rule `sum-widen`, which is in the lowered artifact because it is the same on every target). The rendered script header lists the rules that fired. The matrix lint now runs per target on the rewritten query, so a rewritten construct no longer reports; unmarked ones still do (notes updated on `fn.length` and `fn.try_cast`; the PostgreSQL `fn.try_cast` row stays `unsupported` for what the rules cannot cover: dates and unmarked casts).
- **Probes on the real engines** (before writing the rules): DuckDB `round(2.675::DOUBLE, 2)` is 2.68 and `round(0.285::DOUBLE, 2)` is 0.28 because it rounds `x * 100` in floating point; SQL Server's `ROUND(float, 2)` gave 2.67; PostgreSQL's `round(numeric)` of the double gave 0.29 and 1.01 and `round(double precision, integer)` does not exist. `TRY_CAST('' AS INT)` is 0 and `TRY_CAST('' AS DATE)` is 1900-01-01 on SQL Server. DuckDB accepts `'12.7'` as INTEGER (13) and `'1e3'` (1000), SQL Server returns NULL: not fixable by the rules, documented.
- Tests: 14 unit tests (passthrough, each rule on each target, the shapes each rule leaves alone, rules inside subqueries, the lowerer's marks); two conformance tests on both engines: 11 rows x 8 columns of `length`, `TRY_CAST`, and `round` (positive, zero and negative digits) match DuckDB's results, and `sum` of INT and BIGINT values past 2^31 and 2^63 does not overflow. Unit tests 970, real-engine tests 79.

## 26. Index lint and generation

- `IndexAdvisor` (Models, pure): for each target, looks at the model's load operations and finds the access paths no declared index leads with. Keys (`merge_by_key`, `delete_insert_by_key`, the implicit unique-key load) need a unique index whose leading columns are the key (any order, extra trailing or included columns allowed); watermark, time and range columns need any index leading with the column. An index restricted by `targets:` counts only for those targets, so a model declared on two engines with an index for one gets advice naming the other.
- **DDB-223** (warning): a key-based load with no index on its key. **DDB-224** (note): a key indexed but not unique (your Option B: enforcement is the operator's choice, so this is only a note), or a watermark/time/range column with no leading index. The message names the targets and carries the exact YAML to declare. `plan` shows the same advice (it shares `ProjectChecks`). Advice never blocks.
- Silencing: model-level `lint_ignore: [DDB-223, DDB-224]` (validated: an unknown code is an error) and project-level `lint: { indexes: false }`. Schemas updated.
- **Generation**: the lint message is the paste-ready line; `define` asks for a new model whether to declare the suggested indexes (question `Q-define-<model>-indexes`, options `add_suggested` / `no_indexes`), and `DefinitionWriter` now writes `indexes:`. - Tests: 12 advisor and CLI tests (including that declaring exactly the advised index silences it, and that the generated definition reloads clean), one define test, schema fixtures, golden `define/new_unique_key.yml` now ends with the `indexes:` block. Unit tests 993.

## 30. Runtime parameters and slices (decided with you on 2026-10-02)

- **`plan --param model.operation.parameter=value`** (repeatable): the answer to a parameter's question without an answers file, so a scheduled reload needs no YAML. It becomes the same answer (`provide`) under the same id the planner asks (`Q-param-...`); a value named twice (in `--param`, or in `--param` and the file) is a usage error; a value for a question that is not asked is reported by the existing "answer for an unknown question" warning, which catches typos. `ParseParams` takes the last two dot-separated parts before `=` as operation and parameter, since model names contain dots.
- **Range sanity**: an empty or backwards range (`end <= start`) is now refused (DDB-412) even without a `max_span`; before, only too-long ranges were. At plan time the session reads `MIN` and `MAX` of the range column on the target (`TargetSnapshotReader.ColumnBoundsAsync`, one read-only SELECT each, only for the chosen range operation) and the plan **notes** (`Noticed`, shown in the plan and in `data.noticed`) a range the data does not overlap ("holds rows from X to Y; the range does not overlap them, so the DELETE removes nothing"), and a range into an empty table ("first time"). Never a block: a first load or a gap fill is legitimate. If the bounds cannot be read, nothing is claimed.
- **DDB-225 (warning), the pushdown lint**: `SliceAnalyzer` (`DbDataBuild.Sql/Analysis`) follows a load's slice column (a watermark column, or a range column) down the lowered query through derived tables, CTEs and set operations and reports what prevents the engine filtering early: an aggregate output (naming the aggregate), a window output, a window not partitioned by the column, a LIMIT, DISTINCT ON. It reports only what it can prove (a star or ambiguous name: nothing). The message says why every load then does the whole history's work and what to do instead. **The query is never rewritten** (your decision: advice, not a generated `slice_in_body`); a test shows the rendered load is identical with and without the advice. A custom slicing mechanism chosen by the author is allowed (they write the filter in their query and use `full_replace` or a key load) and is not generated; a first-class operation for it is not built. Silence: `lint_ignore: [DDB-225]`, `lint: { slices: false }`. Schemas, the skill and DESIGN.md 6.6.2 updated.

## 36. Exporting sources from a target (`import-sources`), and source metadata

- **Command**: `dbdatabuild import-sources [schema.table ...] [--target t] [--write | --check]`, effect class target read-only (it writes `sources/` files only with `--write`). It reads columns, native types, nullability and primary keys of the matching tables and views with the read login (`SourceCatalogReader` for the schema list and primary keys, `CatalogReader` for shapes: the same queries planning uses), maps them to logical types (`SourceTypes`: an enumerated table with a fit of exact, widened, lossy or none), and merges with the committed descriptors (`SourceImport`, pure): the live table wins for columns, types and nullability; a committed `grain` and a column the catalog cannot type are kept; a primary key seeds only a new descriptor's grain. The default shows a diff and writes nothing; `--write` writes through `DefinitionFile` (hash-checked, atomic); `--check` fails per stale descriptor. A model's name, the tracking schema and names that cannot be paths are skipped; a damaged descriptor file is never overwritten (`invalid`); a descriptor with no table is reported and kept (`stale`).
- **Diagnostics**: DDB-226 (a column has no logical type: left out, or the committed declaration kept), DDB-227 (descriptor differs from the table), DDB-228 (not importable, or a descriptor with no table).
- **Metadata**: a new document kind `dbdatabuild.source/1` (name, file, definition hash, grain, columns, and the models that read it across the whole project, so the document does not change with the models selected). The project document lists the sources; `metadata` and `validate` print them; `publish-metadata` stores them (everything when no model is named, otherwise the sources those models read), and so does `apply` with `store_on_apply`. **Tracking layout 3**: `metadata_columns` now covers model and source columns and has a `kind` column; targets at layout 2 are refused (DDB-505) until `init --apply`, which re-creates the views. `schemas/metadata.schema.json` and `schemas/output.schema.json` (a closed `data_import_sources`) are updated.
- **Verified**: unit tests for every mapping (1,147 pass), the merge rules, the writer round trip and the metadata documents; on SQL Server 2022 and PostgreSQL 17 (87 real-engine tests pass) one test exports a table with 13 columns of every kind, checks the exact file, validates it, refreshes after an `ALTER TABLE`, keeps a hand-set grain and a hand-typed column, imports a view, skips the tracking schema and a damaged file, reports a stale descriptor, and queries the source documents with SQL. **Not verified**: Fabric; tables with more than a few hundred columns or thousands of tables (each schema is read with one query).
- **Unlimited text stays unlimited** (follow-up to entry 36, at the owner's direction: the length is not the tool's call, and a project that wants to forbid `max` columns writes a unit test over the metadata). A bare `VARCHAR` is now a valid logical type meaning unlimited text: `nvarchar(max)` on SQL Server, `varchar(max)` on Fabric, `text` on PostgreSQL (`varchar(n)` to `text` is a widening change on PostgreSQL, so it plans without a question). `import-sources` maps `varchar(max)`, `nvarchar(max)`, `text`, `ntext` and an unconstrained PostgreSQL `varchar` to `VARCHAR` (exact) and `xml`, `json`, `jsonb` to `VARCHAR` (lossy: read as text); only types with no representation (geography, interval, arrays, user types) are left out (DDB-226). `define` proposes `VARCHAR` (high certainty) for a string column whose length is neither declared upstream nor written in the query, where it used to ask. A committed source type that means the same as the live one is kept as written (a refresh does not replace a hand-put `VARCHAR(500)` on unlimited text). Verified on SQL Server 2022 and PostgreSQL 17 (89 real-engine tests, 1,150 unit tests): a 6,000-character `text` source column passes through a model and a computed `body || '!'` into `nvarchar(max)`/`text` with nothing cut, and the tool then reports the table in sync. **Not covered**: SQL Server cannot index an `nvarchar(max)` key column, and the tool does not warn about it before `apply` (the same is true of a `VARCHAR(5000)`, which already mapped to `nvarchar(max)`); Fabric `varchar(max)` is unverified.

## 39. Lowering: ANY, ALL and row-value IN, and generated aliases

- **A correctness bug found first.** `x op ANY/ALL (subquery)` was *not* refused, as the open-items note said: it lowered, wrongly. DuckDB writes it as a MARK join whose comparison is a join condition; the lowerer read every non-equality condition of a MARK join as a correlation predicate and turned the mark into plain `EXISTS`, so with NULLs `x > ALL (S)` returned rows DuckDB excludes and `x > ANY (S)` as a value said FALSE where DuckDB says NULL (checked in DuckDB itself). Fixed, and the bug is why these now have differential tests with NULLs.
- **Built** (DESIGN.md 7.6): the mark stays symbolic and a filter writes it by what it needs: TRUE as `EXISTS (S WHERE p)`, FALSE as `NOT EXISTS (S WHERE p OR an operand IS NULL)`, following the filter's AND/OR/NOT; a mark used as a value is refused (DDB-324, "used as a value"). Row-value `IN` and `NOT IN` follow the same two forms, with DuckDB's rule that a NULL in any component makes the row unknown (the differential run found that SQL's AND would have disagreed with DuckDB). Subqueries with their own aggregate, window, DISTINCT or LIMIT are wrapped as a derived table. `=` ANY, `<>` ALL stay native `IN`/`NOT IN`.
- **Second bug found by the real-engine test**: a derived-table alias `s1` collided with a *table* called `s1`, so the outer column was captured by the inner alias. Every table and CTE name of the plan is now reserved before aliases (`s1`, `series`, `name_2`) are generated.
- **Verified**: 31 unit cases against DuckDB with seeded NULLs (ANY and ALL with every operator, empty and all-NULL subqueries, correlated, over an aggregate, with LIMIT and DISTINCT, under NOT, OR and AND, in HAVING, row-value IN and NOT IN), 6 refusals of value uses, the alias collisions, and on SQL Server and PostgreSQL 13 filters with NULLs on both sides equal to DuckDB's rows (1,215 unit and 90 real-engine tests pass). **Not verified**: the DuckDB 2.0 alpha, where the plans differ and 9 new tests fail (recorded in OPEN-ITEMS); Fabric.

## 41. Source indexes and foreign keys

- **Exported by `import-sources`** (follow-up to entries 36 and 38): `indexes:` and `foreign_keys:` in the descriptor (`schemas/source.schema.json`, the loader checks that the columns exist, that names are unique and that a foreign key's column counts agree). Indexes come from the catalog shape already read for planning (`ObjectShape.Physical`, parsed back with `IndexText.Parse`); foreign keys are a new read-only catalog query per engine (`SourceCatalogReader.ForeignKeysAsync`). The primary key's own index is the grain and is skipped; an expression index, and an index or foreign key that names a column with no logical type, are left out with a note in the output (`notes`). The live table wins; added, removed and changed indexes and foreign keys are differences (`indexadded`, `foreignkeychanged`, ...), so `--check` finds them. Index names are the table's own, not held to the identifier pattern models use.
- **Metadata**: the source document carries `indexes` and `foreign_keys` (`dbdatabuild.source/1`, closed schema updated) and is published with them; two DuckDB views for rules, `metadata_source_indexes` and `metadata_source_foreign_keys`. ## 58. SQL Server 2025 in the suite, what `version` means, and the regular expressions

- **Built**: a SQL Server 2025 engine in the suite (`scripts/test-engines.sh up mssql2025`, `DBDATABUILD_TEST_MSSQL2025`, the CI group `mssql2025`, and `up all` in the full run); the dialect probes run on it twice, as `sqlserver2025` (database compatibility level 170, told to the tool as version 17) and `sqlserver2025-160` (level 160, version 16); `TargetRules.Apply` takes the configured version, and from 17 SQL Server gets the rules `regexp-full-match` (anchored), `regexp-extract` (`REGEXP_SUBSTR` with the group, `''` for no match or a group that did not take part) and `regexp-replace-first` (`REGEXP_REPLACE` with occurrence 1, or 0 for `'g'`); the matrix rows `fn.regexp_full_match`, `fn.regexp_extract`, `fn.regexp_replace` are `translated, min_version: 17` (the matrix hash changed: goldens regenerated), `fn.regexp` says REGEXP_LIKE needs level 170. Four probes added (first and every match over several matches, a group that did not take part, an alternation in a full match); the Planner, renderer, checks and probes all pass the version to the rules.
- **Findings on a 2025 server**: at level 160 `REGEXP_LIKE` and `REGEXP_SUBSTR` are not recognized but `REGEXP_REPLACE` works, so 2025@160 can do more than 2022 and never less: the single `version` setting (the T-SQL level to generate for; 16 for 2022 and for 2025@160, 17 for 2025@170) is enough, as concluded earlier; the default replace replaces every match (DuckDB: the first); REGEXP_SUBSTR gives NULL where DuckDB gives `''`; `REGEXP_LIKE` is case-sensitive by default whatever the database collation; the transpile rewrites a call of `regexp_replace` as DuckDB's four-argument form and drops what it does not know, so the rule writes a marker name (`ddb_regexp_replace`, spelled out by `TargetRules.Finish`). The whole conformance suite (quick, apply, templates; 109 tests) also passes with the 2025 container standing in for the 2022 one.
- **Verified**: 1,486 unit tests; probes on 2022, 2025@170 and 2025@160 (every regular expression probe agrees with DuckDB at 170, and 2025@160 behaves as 2022 for a project at 16); `A_project_at_version_17_loads_regular_expressions_on_SQL_Server_2025_and_gets_DuckDBs_rows` (init, render, check, plan and apply on 2025@170 and the table equals DuckDB's rows).
- **Not done**: the other things 2025 adds (a native JSON type, vectors) are not used, and the probes found no other difference (the probe corpus is what we have); the `i` and `s` regular expression options; Fabric.

## 59. Oracle's empty string: measured, classified, designed

- **Built**: the probes know an engine that has no empty string (`IProbeEngine.EmptyStringIsNull`, true for Oracle): a case whose answers differ only on the row that holds `''` (id 4) is reported as `empty-string`, a class apart from `DIFFERENT`; five probes about it (`s IS NULL`, `s = ''`, `coalesce`, a `CASE`).

## 61. Nothing that changes with a release in a rendered file

- **Changed**: the rendered load scripts and resolvers no longer have `-- matrix version:` and `-- tool version:` lines, `manifest.yml` no longer has `matrix_version:` and `tool_version:`, and `lowered.sql` no longer has `-- tool version:` (it keeps `-- duckdb:`, the one input of the lowering that is not in the project: an upgrade shows up as a diff on purpose). Reason: a rendered file is a function of the model, the project configuration and the translation rules; whatever in the rule code changes the output changes the text, and the `target rules:` and `type rules:` lines name what fired. A version in the header added no information and made every file of every project differ, with the same SQL, after each release (and after any edit of any matrix row, for the matrix hash), which failed `render --check` in every project's CI and forced a re-render. Nothing read those lines back: they were only written (checked in the code before removing them). The matrix status that applies to a model is in the manifest, per operation.
- **`ProductInfo.Version` follows the release** now: it is the assembly's version, which `scripts/publish.sh` stamps (`VERSION`), and a development build has the one in `Directory.Build.props` (0.3.0), which a release bumps. It is in plans, the JSON documents and the tracking tables as provenance. (It had stayed `0.1.0` since v0.1.0, which is why v0.2.0 and v0.3.0 said 0.1.0 in their documents.)
- **Effect on users**: a project that upgrades re-renders once (`render --write`); the SQL in the scripts is unchanged, the script hashes in the manifests change because the headers are shorter. After that an upgrade changes a rendered file only if its text changes.
- **Verified**: 1,493 unit tests; the goldens differ only by the removed lines and the hashes that follow from them.
- **Left**: a release now bumps `Directory.Build.props`.

## 62. Running queries on one server and writing the results to another: investigation

- **Done** (`docs/research/cross-server.md`; no product code changed): what the code assumes (a target is an engine kind with one read and one write login; sources have no location; a three-part name is refused by the lowering, DDB-324; the gate takes text statements and its one bulk form is a parameterised `INSERT`), and experiments on real engines. **Measured**: SQL Server cross-database names work in a transaction; PostgreSQL has no cross-database queries; a SQL Server linked server pulls fine inside a transaction (1M rows in 8.5 s) but a push inside one fails for lack of a distributed transaction (Linux; Windows would need MSDTC); `postgres_fdw` pulls and pushes inside transactions; DuckDB with its PostgreSQL and community `mssql` extensions moves PostgreSQL to SQL Server (1M rows, 5.1 s) and SQL Server to SQL Server (7.2 s) with DuckDB's own semantics; client-side copy is 190k rows/s with `SqlBulkCopy` against 10k rows/s with the gate's parameterised inserts, so a transfer needs a real bulk API; drivers return different types for one column (`DateOnly` against `DateTime`; 28-digit `decimal`).
- **Proposed**: named connections (`connections:`, source-only connections), a source location with `link` access (physical names at render time, the link checked not created), and a `transfer` step (a query run on one connection, rows bulk-written to a staging table on another, then the existing load strategies) with a `BulkCopy` gate statement; compute at the source later; DuckDB in the middle rejected as a load path (bypasses the gate). Order A (same-server other database), B (links), C (connections), D (transfer), E (compute at the source). Five decisions for the owner are at the end of the note.
- **Left**: everything above is a proposal; the owner's answers on which scenarios come first, whether rows may pass through the machine running the tool, and Fabric decide the order.

## 63. Direction for cross-server work, and a draft of domains

- **Decided by the owner**: no linked servers or foreign servers, no DuckDB in the middle, no support for same-server cross-database queries (views and synonyms outside the tool), connections generalised, and the tool moving the data between connections itself.
- **Drafted** (`docs/research/cross-server.md`, "Domains"): several domains (self-contained folders with their own models, sources and targets) in one repository, with connections defined once at the root, explicit pairing by declaration (`land` on a source, `publish` on a model, never a product of all sources and targets), published outputs as persisted contracts whose consumer-side descriptors are generated and validated offline across domains, and fan-out of raw and transformed data. Open points in the note: names (a domain as a DuckDB catalog), tracking tables per domain, plans and run order across edges, least-privilege connections per domain, incremental movement, partial fan-out and its reconciliation.
- **Left**: no code; the note ends in the decisions that fix the first step.

## 64. Terms and design for connections, copies and fan-in (agreed on paper)

- **Settled with the owner** (`docs/research/cross-server.md`, "Terms" down): a clean break; the project stays the only unit; **connection** (a named database endpoint) replaces "target" for where a model lives and **engine** is the dialect; every table is a **model**, with kinds that build from SQL, **`mapped`** (no body: maps an existing physical table; replaces "source") and **`copy`** (no SQL: `from:` a model on another connection, columns inherited); a query runs against one connection and moving data is always an explicit copy; configuration inherits root, then `_dbdatabuild.yml` per folder, then the model (nearest wins, explicit merge rules, provenance shown); fan-in is a model that exists on several connections (a model's `connections` list, usually set once by a folder's `_dbdatabuild.yml`; there is no separate "group") and a copy that reads from each, with one word, **parameter**, at every scope (project, connection, origin, model, operation; a prefix when referenced: `${origin.store_id}`) used as an added column or as the slice an origin replaces, never a dictated column; per-origin isolation and version-skew reporting. A copy has at most one dimension of expansion. Every folder's `_dbdatabuild.yml` is a project file with the same sections as the root one, layered root-down, with explicit merge rules (`=`, `-`, `+` suffixes) and shown provenance; model parameters are only in the model's file.
- **No code yet.** The note lists the order (connections and the rename; copy with a bulk gate statement; groups and slices; incremental extraction) and four open points (column or row selection in a copy, attribute syntax, drift checks of mapped models at plan, command and key names).
- **Left**: the first build step is the connections-and-rename change, which touches every place that treats a target as an engine; it is a major version.

## 65. Tracking decided: nothing by default, centrally if configured

- **Decided with the owner** (`docs/research/cross-server.md`, "Tracking"): tracking is a setting, not a property of the connection it describes. Default: nothing is tracked, with a **warning** on any command that would have recorded something and no tracking configured; a configured tracking connection that is unreachable is an **error** before anything is touched; offline tracking and catch-up come later. Where: `tracking.connection` and `schema` at the root, overridable per connection (`tracking: none` is the explicit opt-out), never per folder; every tracking row carries its `connection` in its key, so one tracking connection can hold everything; `init` creates the tables once per tracking connection; a plan's steps name their connection and `apply` checks every connection it will use before the first statement. The restore-and-clone worry that argued for local tracking is real only for the data-coupled tables (`run_log` hashes, `operation_interval`) and can be met by cheap checks against the live data; drift fails safe against a central baseline.
- **Written down, not built**: what the tool cannot do with no tracking (drift, the incremental definition block, acknowledgements, history, `report`, `publish-metadata`), and three points the owner then accepted: with no tracking, plans are made from declared against live and changes to existing objects are marked risky; `tracking: none` is the opt-out; no copies to further tracking connections in the first version.
- **Left**: no code.


## 66. Connections in the configuration (first build step of the cross-server work)

## 71. Copies: rows between connections

- **Built** (`DESIGN.md` 6.5.2): `kind: {type: copy, from: schema.table}`. No `.sql`, no `columns` (the origin's), the origin on one connection and the copy on others. A copy is a `full_replace` load over a staging table in the tracking schema, whose generated query and generated mapped table make it flow through lowering, rendering and planning unchanged. `plan` adds a `transfer` step (staging DDL, origin connection, exact read, declared columns), then the load, then a drop of the staging table; `apply` checks and opens every origin before its first statement, streams the one SELECT through `ReadSession`, converts each value by declared logical type (`TransferValues`; errors name the column, not the value) and writes with `GateStatement.BulkCopy` (`SqlBulkCopy` in batches of 20,000, Npgsql binary `COPY`) through the gate, logged as `transfer` with a row count and no values. The staging DDL and the bulk statement are in the dry run. `GateInvariantTests` now also scans for the bulk APIs.
- **Driver setting**: Npgsql's conversion of 0001-01-01 and 9999-12-31 to `-infinity`/`infinity` is off for every connection (`DriverSettings`, called first by the command line and by `LoginSettings`), because a warehouse's "no end date" is a date. A truly infinite value is now an error on read.
- **Plan file**: steps may carry a `transfer:` block (schema and parser updated).
- **Verified on real engines** (`CopyConformanceTests`): SQL Server to PostgreSQL and back, 11 columns of every logical type family, NULLs in every column, unicode, an empty string, a 28-digit decimal, dates and timestamps at their limits, a quote and a newline in text; a dry run creates nothing; the staging table is gone after; a second plan has no DDL; a re-run replaces; 300,000 rows in either direction (about 4 to 6 seconds end to end: plan applied, transfer, load, index); a missing origin login is refused with nothing executed; a decimal wider than the declared type stops the transfer and leaves the destination table empty. Unit tests: planning, conversion, gate logging.
- **Not verified**: Fabric; large objects; time zones other than UTC for `TIMESTAMP WITH TIME ZONE`.
- **Left**: fan-in (several origins), incremental copies, an origin shape check at `plan`, the check that a model's connections have the mapped tables it reads.

- **Built** (`DESIGN.md` 6.5.2): connection `parameters:` (names to single values); `kind.slice` and `kind.on_mismatch` on a copy; a mapped model on several connections; the copy's columns gain the slice column when the origin lacks it (type required), the grain gains it, and the implicit load is `delete_insert_by_key` on it, so a run replaces only the loading origin's rows. ## 74. Tracking: central, per connection, and off by default

- **Built** (`DESIGN.md` 12): `tracking: { connection, schema }` at the project and `connections.<name>.tracking` (`none`, or another connection and schema); `tracking_schema` is gone. The records of a connection live on its tracking connection, which may be another one, with that connection's logins; **every tracking table has a `connection` column** (part of the key where there is one; layout version 4, an older layout is refused by name and cannot be upgraded in place) and every read filters by it. `ApplyEngine` holds a session and a gate per connection through a `Tracker` (a no-op when nothing is tracked); `plan` reads shapes from the data connection and records from the tracking one; `init` creates the tables on a connection that keeps records and tells any other where its records go; `ack`, `report`, `publish-metadata` work through the tracking connection and refuse an untracked one. - **Default is no tracking, with a warning** (DDB-232) on `plan` and `apply`; `tracking: none` is the silent choice. The templates now say `tracking: { connection: sqlserver }`.

- **Not built**: `copy_to` (records replicated to further connections), offline tracking and catching up, a layout upgrade from version 3.

## 75. Incremental copies

- **Built** (`DESIGN.md` 6.5.2): `unique_key` and `watermark: {column, lookback}` under a copy's `kind`. The origin read gains `WHERE <column> >= @watermark`; the bound is the destination's newest value of the column (per origin when there is a slice) less the lookback, worked out at plan time (a read of the destination in the plan's session) and recorded in the transfer step (`watermark: {column, type, value}`, schema and parser updated; bound by the driver, never in the text). Nothing in the destination reads everything. The load is `delete_insert_by_key` on the unique key (plus the slice column). `ReadSession.OpenStreamAsync` takes parameters. The model schema now describes a copy's `slice`, `on_mismatch`, `unique_key` and `watermark`.
- **Verified**: unit tests (validation, the refusals, the planner's read with and without a bound, the plan-file round trip); real engines, both directions (`An_incremental_copy_reads_only_what_changed...`): everything on the first run, then only the rows at or after the newest less the lookback, an edited row within the lookback replaced, a new row added, an old row whose column did not move not read again.
- **Left**: deletes at the origin are not seen (documented; a plain copy reconciles), no way to force a full refresh of one incremental copy short of removing its `watermark`.

## 77. Native models, and local copies

- **Built** (`DESIGN.md` 6.5.4; design `docs/research/native-queries.md`): `kind: {type: native, access: select, query: ...}` or a `.native.sql` beside the definition (never both): a table the engine computes from its own query, declared columns, exactly one connection, a single SELECT (the read guard moved to `Core`; T-SQL may not start with WITH). Queries bind it from the declared columns; on its connection it is **inlined after transpiling** as a derived table in a table's load script and in a view's DDL, its parameters (`${project.x}`, `${connection.x}`, its own `${model.x}`) as placeholders of its own (`@p_native_<model>__<scope>_<name>`) filled by the plan; a view cannot read one with parameters; another connection cannot read it (DDB-231). ## 92. `diff` across connections

- **Built** (`CrossDiffer`, `DiffCommand`, DESIGN.md 9.10): `diff <table> --connection A --against-connection B [--against <schema_name.table_name> | --against-schema <schema name>]`. Each engine computes a digest per value from a canonical text form and only digests are compared: per bucket of key digests first, per row for the buckets that differ. - **Verified**: unit (`CrossDiffTests`: pairing, kinds, reasons, query text); real engines both ways, SQL Server 2022 against PostgreSQL 17 with integers, decimals of different scales, text with accents and `ß`, boolean, date, timestamp, timestamp with zone, uuid, binary, time, fixed-length `char` of different lengths and NULL against the empty string (`CrossDiffConformanceTests`); an identical pair exits 0. **Not verified**: Fabric; tables of millions of rows (the digest query scans the table on each side); SQL Server 2025.
- **Limits**: floating point is not compared; a PostgreSQL `numeric` without precision is not compared; there is no row filter.

## 105. Cross-connection `diff` at scale, and an unhandled driver error that was not scrubbed

## 106. A statement of `apply` had the drivers' 30-second timeout

- **Found** by going looking for other default timeouts after entry 105: every statement `apply` ran through the gate (`MutationGate.ExecuteAsync`: DDL, loads, hooks, index creation) had the driver's default command timeout, 30 seconds on both Microsoft.Data.SqlClient and Npgsql. The conformance tests never ran a statement that long.

## 107. A project of hundreds of models: validation grew with the square of the models

- **Measured** (a generated project: 10 mapped tables and 100 or 300 models, each a join of two earlier tables, Debug build): `validate` took 9.1 s for 100 models and 59 s for 300; `render --write` 60 s; `metadata` 62 s. The time per model rose from 0.09 s to 0.2 s: not linear.

- **Fixed** (`ModelLowering.UpstreamFor`): DuckDB is given only the declared tables the query's text names (found by the parser); every table when the query reaches a macro (a macro can name a table through an argument) or its text cannot be read. - **After**: `validate` 3.3 s for 100 models and 8.8 s for 300; `render --check` 8.5 s; `metadata` 11.6 s; `loads` 3.3 s; `graph --columns` 2 s. Output is byte-identical (the unit suite, with its goldens, passes). **Not done**: `plan` on such a project (it needs a database; the planner's own cost was not measured), and a release build (the numbers are Debug).

## 108. `apply` re-read the schemas of every object under the schema name after every step

- **Measured** (the generated project of entry 107, 300 models in one schema name on PostgreSQL 17, 401 steps): `apply` took 199 s, 0.5 s a step.
- **Cause**: after each DDL step (and in the staleness check of each base object) the executor read the live shape of the object it had just touched through `CatalogReader.ReadObjectsAsync`, which read **every** table and view of the schema name (two catalog queries, about 1,200 rows) and then picked one: the cost of a step grew with the objects in the schema name, and an apply with the square of them.
- **Fixed**: `ReadObjectsAsync` takes an optional object name and the four catalog queries filter on it (`@object`); the executor asks for the one object. Planning still reads each schema name once.
- **After**: the same plan applies in 9 s (a twentieth). A plan, `plan` again after the apply and `report` take 12 s and 1.5 s; the plan's own time is the offline checks of entry 107.

## 114. Cross-connection `diff` when most rows differ

- **Found by reading my own design**: the second level of `diff --against-connection` fetches the digest of every row of the buckets that differ. When a column differs systematically between two engines (the likeliest reason to compare them), every bucket differs and the fetch is every row: 5 million rows of six digests is more than a gigabyte of strings.
- **Built** (`CrossDiffer.MaxDrillRows`, `PartialDiff`): when the buckets that differ hold more than 1,000,000 rows (the larger side), the comparison stops after the first level and says so: the JSON has `rows.partial` (`buckets_differing`, `buckets`, `rows_in_differing_buckets`, `columns_differing`; `identical` is false, the row counts are not known), and the text names the columns whose values differ in some bucket and suggests `--exclude-columns` or `--columns` to look at the rest row by row.
- **Verified** (SQL Server 2022 against PostgreSQL 17): with the limit lowered to 1,000 and every one of 5,000 rows different in one column, the result is partial and names that column; leaving it out with `--exclude-columns` compares the other columns row by row and finds them identical (exit 0). The limit itself (1,000,000) was not exercised on a table that large.
- **Also seen under Wine** (`scripts/test-windows-wine.sh`, unit suite, 1,786 run): 5 failures, none in code touched by this work: two tests need `git`, which is not in the Wine prefix (the old `changed:` test and the new one), two web-server tests (a symbolic link and a loopback request, Wine's semantics), and the agent-kit schema comparison, which failed only because a schema was edited while the run was in progress. Windows itself passes in CI on every push.

## 115. The history read takes only the plans that hold a history answer

- **Found** while checking the cost of entry 100: `plan` now reads the column history on every run, and `HistoryReader` read the full text of every completed plan to look for answers (`Q-history-...`). A plan of 400 steps is hundreds of kilobytes, so the read grew with the number of applies the connection has ever had.
- **Changed** (`HistoryReader`): the query keeps only plans whose text contains `Q-history-` (`LIKE` on the plan text, on both engines). The history report and DDB-240 are built from those answers and nothing else, so what they say does not change. A plan that cannot be read back is now only reported when its text still holds a history answer.
- **Verified**: the history, `run` and JSON-command conformance tests on both engines pass unchanged.

## 116. `plan` timed out once the tracking log tables held a few hundred thousand rows (PostgreSQL)

- **Found** by filling the tracking tables the way a year of scheduled runs would (`run_log` and `ddl_log`, 200,000 rows each, synthetic): on PostgreSQL 17 `plan` took 48 s and then failed with a driver timeout (reported as DDB-242). The snapshot read the newest `ok` row of each object and model with `... = (SELECT MAX(...) FROM same_table x WHERE x.object = d.object)`, a correlated subquery that PostgreSQL runs once per row, and neither log table has an index on the columns it matches. The work grew with the square of the log.
- **Fixed** (`TargetSnapshotReader.ReadAsync`): both reads use `ROW_NUMBER() OVER (PARTITION BY object ORDER BY time DESC)` and keep the first row: one pass, and exactly one row per object even when two rows share a timestamp (the old query could return both, and building the dictionary from them would have thrown). `schema_version` keeps its correlated form: its primary key is `(connection, object_name, first_seen_utc)`, so the subquery is an index seek.
- **After**: with 4,000,000 rows in the two tables on PostgreSQL, `plan` takes 14.6 s (13 s with almost no history), `check` 14.7 s and `report` 4.3 s; with 2,000,000 rows on SQL Server 2022, 14 s, 12.8 s and 1.8 s. SQL Server's optimizer had coped with the old form; the new one is the same on both.
- **Not measured**: the same history with many connections sharing one tracking schema name; a tracking schema name on another server (the reads then cross a network).

## 117. The history read asks only about the models that have a history answer

## 120. Non-ASCII text literals were lost on SQL Server

## 121. A decimal constant wider than 18 digits could not be lowered

- **Found** by a probe that selects a constant of each type (`Constants_of_every_type_come_back_exactly_from_a_load_on_both_engines`): `CAST(123456789012345678901234567890.123456 AS DECIMAL(36, 6))` stopped `render` with DDB-324 ("a plan shape the lowerer does not handle (FormatException)"). - **Fixed** (`PlanLowerer.IntegerValue`): the value is `upper * 2^64 + lower`; used for decimal constants and for integer constants of a wide type. Four unit cases (30 digits, negative with 38, 24 decimal places, 38 nines) equal DuckDB's own text for the lowered query.
- **Verified**: a model of constants on SQL Server 2022 and PostgreSQL 17 returns a timestamp with microseconds, the first and last date, a 36-digit decimal, a small negative decimal, the largest and smallest `BIGINT`, both booleans, a typed NULL, the empty string, two spaces (kept, length 2), a uuid and a `DOUBLE` of 1.5e300 exactly as DuckDB has them. ## 122. A copy of a zoned timestamp from SQL Server to PostgreSQL failed

## 125. Ctrl-C during an apply

- **Found** while reading how the CLI stops: the rule "a statement that has started is never abandoned" held for the terminal and web interfaces (a stop flag the apply loop checks between steps) but not for the command line, where Ctrl-C ended the process in the middle of a statement and left a `started` step with no outcome.
- **Changed** (`ApplyCommand`): when `apply` (and so `run`) is not hosted by an interface with its own stop, the first Ctrl-C sets the stop flag and prints a line ("the apply stops after the step that is running; press Ctrl-C again to end it now"); the apply loop stops before the next step (DDB-445 "Apply was stopped by the operator", exit 1) and the plan is resumable. The second Ctrl-C is the default: the process ends. A dry run keeps the default behaviour.
- **Verified** (SQL Server 2022 and PostgreSQL 17, Linux, the real executable in its own process with SIGINT): during a 6-second hook the signal is sent; the apply finishes the hook, runs nothing after it, exits 1 with DDB-445, and `apply --resume` completes the plan. - **Not verified**: Windows (Ctrl-C there is the same event in .NET; no test).

## 126. `current_timestamp` and `now()`

- **Found** by writing a model that stamps its rows (`SELECT ..., now() AS loaded_at, current_timestamp AS t2, current_date AS d`) and reading the rendered text: (1) `current_timestamp` is bound by DuckDB as `get_current_timestamp()`, which the lowered query kept and neither engine has, so a model that used it failed at `apply` on both SQL Server and PostgreSQL; (2) `now()` became `GETDATE()` on SQL Server, the server's local clock *without a zone*, which a `TIMESTAMP WITH TIME ZONE` column reads as UTC: right only on a server at UTC, wrong by the offset on any other (DuckDB's `now()` is a point in time).
- **Fixed**: (1) the lowerer writes `get_current_timestamp()` as `now()` (the same value, and a function the transpile knows). (2) a new target rule `now-with-zone` for SQL Server writes `now()` as `SYSDATETIMEOFFSET()` (marker `ddb_sysdatetimeoffset`, replaced in `TargetRules.Finish`); it is in `RewriteCatalog`, the JSON Schemas' rule lists and can be turned off like the others (`rewrites: {disable: [now-with-zone]}`). `current_date`, `today()`, `localtimestamp` and `current_time` stay on the local clock (`GETDATE()`, cast), as before.
- **Verified**: unit (`TargetRulesTests`: the rule fires on SQL Server and not on PostgreSQL, a cast of it, `date_trunc` of it); SQL Server 2022 and PostgreSQL 17 load `now()` and `current_timestamp` into zoned columns within five minutes of the engine's own clock (`The_current_time_is_loaded_as_the_instant_it_is_on_both_engines`). **Not verified**: the rule on Fabric (not applied: unverified).

## 129. `show` for a host without the MCP app: a one-time link

- **Why**: on 0.3.1 the owner's session in Claude Code (Claude Desktop, Windows) answered "not through this server" when asked for a screen: `show` was offered only to hosts that advertise MCP Apps, and the skill describes it as if it were always there.
- **Built** (`McpServer.ShowByLink`, `WebServer` one-time links): `show` is always listed. For a host without the app it starts the web page on the loopback address (once per server, read-only; `--allow-apply` as for the app), and the result is a link `http://127.0.0.1:<port>/?token=...&screen=<screen>` that works once and for ten minutes. Opening it spends the link, sets a session cookie and redirects to the address without the token; the page keeps the session token for its calls; the API accepts only a session token (a link is not one). The first screen is the one asked for. `dbdatabuild web` is unchanged. The server's connect line on standard error and the skill now say what `show` does in each kind of host.
- **Limit, stated plainly**: the link is in the model's hands before it is in the person's, so whoever opens it first gets the session. The model is told not to; a model that can run commands could. The one-time rule keeps the link's text from working later, in a transcript or a log; it does not make the model unable to look at the page. Everything the page can do is what the read-only commands and (with `--allow-apply`) the person's Apply button can do; `--show-values` and sample data are in the page as they are in `dbdatabuild web`, so the model-sees-no-data rule rests on the model not using the link.
- **Switch** (added after review): `dbdatabuild mcp --no-show` removes the `show` tool for every host. The owner's rule for this: the defaults are guardrails that keep the agent doing the right thing, real barriers are the logins and the `--allow-*` options, and a reasonable simple scenario gets no extra guards (so no confirmation step on the link).
- **Verified**: unit (`OneTimeLinkTests`: the redirect, the cookie, the page and the API with the session, the spent link, a link used as a session token, a stranger, two sessions; `McpServerTests`: `show` in a host without the app returns the link, which opens once). Not verified: in a real host, and on Windows.

## 138. Refresh runs from a compiled plan; tracking layout 5 (phases 4 and 5 of the lifecycle plan)

- **The compiled plan**: `project compile` writes `rendered/<connection>/refresh.plan.yml` for each connection (`RefreshPlanBuilder`, `RefreshPlanDocument`): the routine loads in dependency order (each model's default operation, with the load script and resolver by path and hash, the values the project's files give, the watermark's `on_null`/`initial`, and the safe data hooks around it), `requires` (the shape the declared columns give each loaded table, as the engine reports it), `project_hash` (a hash over the expected structure of the whole connection: each table model's shape, each view's definition) and `excluded` (models with loads that are not routine, each with the reason: a copy, a load that needs a value from a person, a hook that is not a safe data hook). The file carries a hash of its own content like a deploy plan, is deterministic, and is checked by `project compile --check` like any rendered file. A change of a parameter value changes it (and no load script).
- **`connection refresh`** (`RefreshCommand`, replacing `RunCommand`): reads that plan and the scripts it names (each must have the recorded hash, DDB-448; a missing plan is DDB-446), applies `refresh.check` or `--check` (**none**: nothing; **project**: the project's `project_hash` against the last completed deploy's; **objects**, the default: each loaded object against the latest recorded shape, tracking tables only; **live**: against the catalog, and a change made outside the tool is named), stops on a failure before anything runs (DDB-447) or runs anyway with `--on-fail warn`, finds the watermarks with the resolvers, and runs the loads through `ApplyEngine` in refresh mode: no plan is verified against the live objects, no catalog read per load unless the check is `live`, nothing to continue, an event of its own (`ref-<utc>-<4 hex>`) in `migration_log` with `lane = 'refresh'` and the compiled plan's hash; the plan text is kept only when `plans.refresh.audit` is `full`. It writes no plan file. The test gate and the recording of native definitions and metadata belong to deploy and are not run by a refresh.
- **Layout 5**: `migration_log` has `lane` and `project_hash`; a deploy records its lane and the project hash its plan carried (`Plan.ProjectHash`, in the plan file and `schemas/plan.schema.json`). The init script never alters, so `init --apply` on a layout 4 store does not claim it (the version row is written only when the newest column is there) and the tool keeps saying `init --upgrade`; the upgrade adds the two columns. `StatusAsync` reads the version table directly instead of asking the catalog whether it exists, so the readiness check is no metadata query.
- **`connection monitor`**: a failed refresh is something to attend to only until a later refresh completes; the message for a deploy that did not complete says to apply the same plan again.
- **Defaults**: `plans.deploy.require_clean_tree` is true by default (the guard that was there stays) and applies to a refresh as well.
- **Tests**: `RefreshPlanTests` (the builder, determinism, tampering and damage), `RefreshTests` (the command up to the point where a connection is needed), `ProjectConfigTests` (the new settings), `TrackingUpgradeConformanceTests` (4 to 5 on both engines), and the conformance test `Refresh_runs_the_compiled_routine_loads_under_the_check_chosen_and_each_run_is_an_event` (every check against a real deploy, a model change, a change made outside the tool, the engine's own error with `--check none`, and a spy on the read session proving `--check none` issues no catalog query).
- **Not done**: `plans.*.keep` database and ephemeral (and the `plan_store` table), the deploy event as its own id, `audit` for a deploy, statement-log retention, `connection status` and `monitor` as the traffic-light views, `refresh` of copies.
- **Verified**: unit suite and the conformance groups on SQL Server 2022 and PostgreSQL 17 (see the next entry for the full run). Fabric not run.

## 140. The plan policy acts: ephemeral plans, audit levels, statement-log retention; lanes in the interfaces (phases 5, 7 and 8)

- **`plans.deploy.keep: ephemeral`**: planning writes the files under `.dbdatabuild/plans/<connection>/` (git ignores that folder; `--output` still wins) instead of `plans/`, and applying a plan from there removes the files once it succeeded. **`keep: database`** is refused with a message that says it is not built yet.
